[Part 1](/blog/sre-guide-deploying-llms-part-1/) was about what an LLM is, [part 2](/blog/sre-guide-deploying-llms-part-2/) was about how it becomes an assistant and what it costs to serve, and [part 3](/blog/sre-guide-deploying-llms-part-3/) was about the chips and the engines you can run it on. Now it's time to combine what we learned in all three and use it to build a scalable deployment of Qwen3.8-27B on AWS using [Kubernetes](https://kubernetes.io/).

We'll do it in three steps. First we provision the infrastructure, which covers the journey of loading the model and serving it from pods running on GPUs. Then we look at networking and request routing, which is how we make smart use of those loaded models and get the most cache hits out of them. Finally we talk about how to observe the whole setup, and how to use what we see to make it autoscale.

Everything in this part is infrastructure as code. [Terraform](https://developer.hashicorp.com/terraform) creates everything that lives in AWS and the add-ons the cluster needs: the network, the cluster, the storage bucket for the weights, the permissions, and the controllers we'll install. A [Helm](https://helm.sh/) chart creates everything that runs in Kubernetes for the model: the GPU nodes it asks for, the [vLLM](https://docs.vllm.ai/) pods, the routing, the autoscaler and the alert rules. Each tool does what it's good at. Terraform is built for cloud resources and for the order they have to be created in. Helm is built for packaging Kubernetes objects and configuring them from one values file. We keep the Kubernetes custom resources in Helm, because Terraform's Kubernetes provider needs a custom resource definition to exist before it can even plan, and that gets awkward quickly.

For every Kubernetes resource we use, we'll first look at the plain YAML and go through what its important fields mean, and then turn it into a template in the chart. All of the code is in the [examples folder](https://github.com/codemug/codemug.github.io/tree/main/public/examples/sre-guide-part-4) of this blog's repository, so you can follow along or run it yourself.

## 1. Pick a region and a machine

Since we're using AWS, our first step is to pick an appropriate region to deploy this workload in, and for that we need to look at what is available where. Don't worry about getting it perfect. Because we're using IaC, if you change your mind later you can apply the same code in a different region.

The machine decides which regions we can even use, so let's start there. Part 3 ended its AWS section on the [g7e family](https://aws.amazon.com/ec2/instance-types/g7e/): an NVIDIA RTX PRO 6000 Blackwell with 96 GB of GDDR7 per GPU, 1,597 GB/s of memory bandwidth and native FP4. A 27B model quantized to [NVFP4](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/) is exactly what it's made for, so that's our machine. The family comes in six sizes. What changes along the ladder is how many GPUs you get and how much host (CPU, RAM and network) comes with them.

Source: the [EC2 accelerated computing instance specifications](https://docs.aws.amazon.com/ec2/latest/instancetypes/ac.html) and the g7e product page, read at the time of this deployment.

We'll use the smallest size, `g7e.2xlarge`, with one GPU per node. There are three reasons:

- The NVFP4 checkpoint we're using weighs about 20 GiB, so the model fits on one card and still leaves most of the 96 GB for the [KV cache](/blog/sre-guide-deploying-llms-part-2/#kv-caching-and-prefilldecode).
- A model that fits on one card gains nothing from a second one on the same node. The RTX PRO 6000 has no [NVLink](/blog/sre-guide-deploying-llms-part-3/#nvidia), as part 3 pointed out, so splitting the model across GPUs would pay the PCIe cost on every layer for no benefit.
- One GPU per node makes the pod the unit of failure and the unit of scaling. If a node dies we lose exactly one replica, and adding capacity means adding exactly one GPU.

The host around the GPU is small, 8 vCPUs and 64 GiB, but vLLM doesn't need much of it. Our pod will ask for 6 vCPUs, and whatever is left on the node stays available to any other pod that tolerates the GPU [taint](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/).

Now, where can we get it? At the time of this deployment, the AWS [instance types by Region](https://docs.aws.amazon.com/ec2/latest/instancetypes/ec2-instance-regions.html) page lists g7e in 13 of its 39 Regions: us-east-1, us-east-2, us-west-2, ap-south-1, ap-northeast-1, ap-northeast-2, ap-southeast-3, ap-southeast-5, ap-southeast-7, eu-central-1, eu-west-2, eu-south-2 and eu-north-1. It's not in Ireland, Singapore or N. California, which are the regions people tend to reach for first. That page lists Regions and not Availability Zones, and AWS warns that a type supported in a Region might not be supported in every zone. So the second check is the zone, and it's one read-only call:

```bash
aws ec2 describe-instance-type-offerings \
  --location-type availability-zone \
  --filters Name=instance-type,Values=g7e.2xlarge \
  --region us-east-1 \
  --query 'InstanceTypeOfferings[].Location' --output text
```

We don't want to rely on remembering to run that. In our Terraform the region is one variable, and the same check runs as a guard before anything gets created: if the region you pick has no `g7e.2xlarge`, Terraform stops with a clear message.

```hcl
# terraform/variables.tf (lines 1 to 10)
# The only value that changes when you re-apply this in another region.
variable "region" {
  description = "AWS region to deploy into"
  type        = string

  validation {
    condition     = can(regex("^[a-z]{2}(-[a-z]+)-[0-9]+$", var.region))
    error_message = "region must be an AWS region name such as us-east-1."
  }
}
```

```hcl
# terraform/checks.tf
# Fails the plan in a region that does not offer g7e.2xlarge, the GPU
# instance the NodePool requests. The IaC form of "does this machine
# exist in this region".

data "aws_ec2_instance_type_offerings" "g7e" {
  location_type = "availability-zone"

  filter {
    name   = "instance-type"
    values = ["g7e.2xlarge"]
  }

  lifecycle {
    postcondition {
      condition     = length(self.locations) > 0
      error_message = "g7e.2xlarge is not offered in ${var.region}. Pick a region from the list in section 1."
    }
  }
}
```

The third check is quota, and it's the one that stops people on launch day. [EC2 quotas](https://docs.aws.amazon.com/ec2/latest/instancetypes/ec2-instance-quotas.html) for GPU instances are counted in vCPUs. The quota that covers g7e is called `Running On-Demand G and VT instances`, and there's a separate `All G and VT Spot Instance Requests` quota for spot. Both default to 0. A `g7e.2xlarge` is 8 vCPUs, so ten of them need 80 vCPUs of quota, and a quota of 192 vCPUs buys you exactly one `g7e.48xlarge`. So ask before you need it:

```bash
# current value, in vCPUs (L-DB2E81BA is the on-demand G and VT quota, L-3819A6DF the spot one)
aws service-quotas get-service-quota --service-code ec2 \
  --quota-code L-DB2E81BA --region us-east-1 --query Quota.Value

# ask for 80 vCPUs: ten g7e.2xlarge
aws service-quotas request-service-quota-increase --service-code ec2 \
  --quota-code L-DB2E81BA --desired-value 80 --region us-east-1
```

<DeckFig name="p4-regions-quota" />

Terraform can send the same request for us. It's off by default, because it should be a deliberate decision, and you turn it on by setting `gpu_quota_vcpus`.

```hcl
# terraform/quota.tf
# Optional quota request. A new account in a new region cannot launch
# g7e until the On-Demand G and VT vCPU quota (L-DB2E81BA) is raised;
# gpu_quota_vcpus requests it here, 0 leaves the account default.

resource "aws_servicequotas_service_quota" "gpu_vcpus" {
  count = var.gpu_quota_vcpus > 0 ? 1 : 0

  service_code = "ec2"
  quota_code   = "L-DB2E81BA"
  value        = var.gpu_quota_vcpus
}
```

The last decision is how we buy the capacity. [Capacity Blocks for ML](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-blocks.html) are the product people mention first, but g7e isn't on their supported list, which today covers the P4, P5 and P6 families and Trainium. For a g7e fleet, the way to guarantee capacity is an [On-Demand Capacity Reservation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-reservations.html), which works for the G family. [Spot](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/using-spot-instances.html) is the cheap overflow, with a two-minute interruption notice. We treat it as overflow and not as the floor, because a replacement pod needs a new node, a pulled image and loaded weights before it serves anything. [Karpenter](https://karpenter.sh/docs/), which we meet in the next section, understands all three and tries them in that order: reserved, then spot, then on-demand. Prices move, so we won't quote any here: part 3 has the approximate ones, and the pricing page has the real ones.

One last thing about changing your mind. Applying the same Terraform in another region gets you a new cluster, but a few things don't move with it. The weights in the [S3](https://aws.amazon.com/s3/) bucket don't, because a bucket lives in one region, and if the first bucket still exists the new one needs a different `model_bucket_name`, since S3 bucket names are global. The quota and any capacity reservation don't move either. Those are the things to redo.

That's the first gate: a GPU of the right kind has to exist in a zone we can reach, under a quota that is larger than zero. Next comes the node layer.

## 2. The node layer: EKS, Karpenter and Bottlerocket

Next we need a Kubernetes cluster that can give us a GPU node whenever a pod asks for one. Three pieces do that. [EKS](https://docs.aws.amazon.com/eks/latest/userguide/what-is-eks.html) is the Kubernetes control plane, Karpenter creates the nodes, and [Bottlerocket](https://bottlerocket.dev/) is the operating system those nodes run. We'll do it in two steps. First Terraform creates the cluster and the AWS side of Karpenter. Then we describe the GPU nodes we want as Kubernetes YAML and turn that into templates in our chart.

### The cluster, with Terraform

EKS currently supports Kubernetes 1.34 to 1.37 in standard support, and Karpenter v1.15, the release we're using, is the first one that supports 1.37. We'll deploy 1.35. The cluster itself is a thin layer on top of the community EKS module: the control plane, the core add-ons, and one small [managed node group](https://docs.aws.amazon.com/eks/latest/userguide/managed-node-groups.html) called `system`.

```hcl
# terraform/eks.tf
# EKS cluster. Both API endpoints are enabled: private for in-cluster
# access, public (restricted to var.api_allowed_cidrs) so `aws eks
# update-kubeconfig` works from your machine.

module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "21.29.0"

  name               = var.cluster_name
  kubernetes_version = var.kubernetes_version

  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnets

  create_iam_role = true

  endpoint_private_access      = true
  endpoint_public_access       = true
  endpoint_public_access_cidrs = var.api_allowed_cidrs

  # The deploying identity keeps admin permissions so that
  # `aws eks update-kubeconfig` works.
  enable_cluster_creator_admin_permissions = true

  # The addons that ship with the cluster. Empty object = the module's
  # (most recent) addon version.
  addons = {
    vpc-cni                  = {}
    kube-proxy               = {}
    coredns                  = {}
    "eks-pod-identity-agent" = {}
  }

  # Small system node group: hosts Karpenter, the gateway data plane,
  # KEDA, Prometheus and the picker. Bottlerocket x86; the module picks
  # the newest EKS-optimized Bottlerocket AMI for this Kubernetes version.
  eks_managed_node_groups = {
    system = {
      ami_type       = "BOTTLEROCKET_x86_64"
      instance_types = [var.system_instance_type]

      min_size     = var.system_node_group_min_size
      max_size     = var.system_node_group_max_size
      desired_size = var.system_node_group_desired_size
    }
  }

  # Karpenter discovers node-group capacity through this tag on the
  # node security group.
  node_security_group_tags = {
    "karpenter.sh/discovery" = var.cluster_name
  }

  tags = var.tags
}
```

Two settings are worth a look. The API endpoint is public but restricted to `api_allowed_cidrs`, which defaults to everywhere so the example works out of the box. Narrow it before you use the cluster for anything real. And the `system` group takes the newest Bottlerocket [AMI](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/AMIs.html) for the Kubernetes version, while the GPU nodes use the release pinned in the node class below.

That `system` node group exists because Karpenter can't launch the node it runs on. The Karpenter controller, the gateway, [KEDA](https://keda.sh/), [Prometheus](https://prometheus.io/) and the [endpoint picker](https://gateway-api-inference-extension.sigs.k8s.io/concepts/api-overview/) (all of which we meet later) are ordinary CPU pods, and they live here. The GPU nodes come only from Karpenter.

The module also has a Karpenter submodule, which creates the AWS side of Karpenter for us: the IAM role that the new nodes run with, a queue that receives Spot interruption and instance-health events, and the identity the controller uses to call EC2. Terraform then installs Karpenter itself with Helm.

```hcl
# terraform/karpenter.tf
# Karpenter, the AWS side: the node IAM role + instance profile for the
# nodes Karpenter provisions, the SQS interruption queue (the two-minute
# Spot notice), and the controller identity via EKS Pod Identity. The
# association points at a service account the chart release below
# creates; EKS Pod Identity associations are eventually consistent.

module "karpenter" {
  source  = "terraform-aws-modules/eks/aws//modules/karpenter"
  version = "21.29.0"

  cluster_name = var.cluster_name
  region       = var.region

  namespace       = "karpenter"
  service_account = "karpenter"

  # The Pod Identity association is created by default in the submodule.
  enable_spot_termination = true
  tags                    = var.tags

  # The access entry and the association need a running cluster.
  depends_on = [module.eks]
}

resource "helm_release" "karpenter" {
  name             = "karpenter"
  repository       = "oci://public.ecr.aws/karpenter"
  chart            = "karpenter"
  version          = "1.15.1"
  namespace        = "karpenter"
  create_namespace = true

  # serviceAccount.name is pinned to the association above. The
  # EC2NodeClass in the model chart uses the node role from output
  # node_role_name.
  values = [yamlencode({
    serviceAccount = {
      name = "karpenter"
    }
    settings = {
      clusterName       = var.cluster_name
      interruptionQueue = module.karpenter.queue_name
    }
  })]
}
```

### How Karpenter works

Karpenter is a node autoscaler that starts from pending pods and not from node groups. There's no pre-defined pool of identical instances to grow or shrink. It watches for pods the scheduler has marked unschedulable, looks at what they ask for, and launches an instance of whatever shape fits. When a node is no longer needed it removes it again. Karpenter launches the node; the [kube-scheduler](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/) still places the pod on it.

Two objects configure it, and both are cluster-scoped. A [`NodePool`](https://karpenter.sh/docs/concepts/nodepools/) says what Karpenter is allowed to launch, and an [`EC2NodeClass`](https://karpenter.sh/docs/concepts/nodeclasses/) says how those nodes are built.

### The NodePool

Here's the raw YAML for our GPU pool:

```yaml
# k8s/nodepool.yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: g7e
spec:
  template:
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: g7e
      requirements:
        - key: karpenter.k8s.aws/instance-family
          operator: In
          values: ["g7e"]
        - key: karpenter.k8s.aws/instance-gpu-manufacturer
          operator: In
          values: ["nvidia"]
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64"]
        # priority is reserved, then spot, then on-demand; Karpenter only falls back to types listed here.
        # "reserved" has no effect until the EC2NodeClass selects a capacity reservation.
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["reserved", "spot", "on-demand"]
      # keep non-GPU pods off these expensive nodes
      taints:
        - key: nvidia.com/gpu
          value: "true"
          effect: NoSchedule
      # a maximum lifetime, not a schedule: drift or emptiness can remove a node earlier
      expireAfter: 720h
  limits:
    nodes: 10
  disruption:
    # never repack a running model server to save money: only a node with no pods left is a candidate
    consolidationPolicy: WhenEmpty
    # and only after it has stayed empty for 30 minutes
    consolidateAfter: 30m
```

The requirements pin the pool to g7e and NVIDIA GPUs. The `capacity-type` line is the priority order from section 1: reserved, then spot, then on-demand. Karpenter only falls back to types that are listed, and `reserved` has no effect until the node class selects a capacity reservation. The taint keeps everything that doesn't ask for a GPU off these expensive nodes. `limits.nodes` is the safety catch: ten nodes is the most this pool can ever cost us. And `expireAfter` is a maximum lifetime, not a schedule: [drift](https://karpenter.sh/docs/concepts/disruption/#drift) or emptiness can remove a node earlier.

The disruption block is the part to think about for LLM serving. Karpenter's default policy is `WhenEmptyOrUnderutilized` with a `consolidateAfter` of `0s`, which means it repacks pods onto fewer or cheaper nodes whenever it can. That's free for a stateless web pod, but for a vLLM pod it means a new node and a model reload. We don't want these nodes disrupted, so we use `WhenEmpty`, which only looks at nodes that have no pods left. Then `consolidateAfter: 30m` makes a node stay empty for half an hour first, so a scale-in followed by a scale-out a few minutes later reuses the node instead of paying for a new launch, an image pull and a model load.

Two other things can still replace a node, and neither depends on that policy. Drift replaces a node that no longer matches its `NodePool` or the node class it was built from, and a new AMI is the usual cause. Expiry removes it at `expireAfter`, which defaults to 720 hours. [Disruption budgets](https://karpenter.sh/docs/concepts/disruption/#nodepool-disruption-budgets), which default to 10 percent of nodes at a time, limit drift and consolidation but don't block expiration.

### The EC2NodeClass

The second object says how those nodes are built:

```yaml
# k8s/ec2nodeclass.yaml
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: g7e
spec:
  # Bottlerocket; for GPU instance types Karpenter resolves this to the aws-k8s-nvidia variant.
  # Pin a version: "latest" would drift every node whenever a new AMI is published.
  amiSelectorTerms:
    - alias: bottlerocket@v1.68.0
  role: example-karpenter-node-role
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: example-cluster
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: example-cluster
  # format the local NVMe as RAID0 and make it the node's ephemeral storage
  # (automatic on Bottlerocket v1.22.0 and later)
  instanceStorePolicy: RAID0
  # uncomment to use an On-Demand Capacity Reservation first (Beta in Karpenter v1.15)
  # capacityReservationSelectorTerms:
  #   - id: cr-11111111111111111
  tags:
    karpenter.sh/discovery: example-cluster
```

Four lines carry most of the weight:

- The AMI alias is pinned to a Bottlerocket release. If we used `latest`, every node would drift, and be replaced, whenever AWS published a new image. There's no separate switch for the NVIDIA variant: Karpenter resolves the alias to several image parameters and picks the `aws-k8s-nvidia` one for instance types that report a GPU count, which every g7e size does.
- `role` is the IAM role the nodes run with. It's the one Terraform just created.
- The subnet and security group selector terms are required: the schema rejects an `EC2NodeClass` without them, which is easy to miss when you copy a trimmed example. They match the `karpenter.sh/discovery` tag that Terraform put on our subnets and security group.
- `instanceStorePolicy: RAID0` formats the local NVMe drive and makes it the node's ephemeral storage, so an [`emptyDir`](https://kubernetes.io/docs/concepts/storage/volumes/#emptydir) lands on a fast, large, local disk. We'll use that in section 7.

### Turning them into templates

Now let's do the same thing as a Helm template. Look at what changed from the raw YAML: the node role and the discovery tag are no longer written into the object, because they belong to the cluster and not to the model. Terraform prints them as an output, and the chart reads them from its values.

```yaml
# helm/llm-serving/values.yaml (karpenter)
# Karpenter GPU pool: NodePool + EC2NodeClass, and the AWS-side inputs from `terraform output chart_values_yaml`.

  poolName: g7e
  nodeRole: example-karpenter-node-role
  discoveryTag: example-cluster
  amiAlias: bottlerocket@v1.68.0
```

### Why Bottlerocket

Bottlerocket is an operating system built for running containers and nothing else, and for GPU inference nodes it removes more work than it adds. The root filesystem is read-only and verified with [dm-verity](https://docs.kernel.org/admin-guide/device-mapper/verity.html), `/etc` is a tmpfs, [SELinux](https://www.redhat.com/en/topics/linux/what-is-selinux) is enforcing, and there's no shell, no SSH server and no package manager on the node. You configure it through a settings API that you set from user data as TOML, and when you have to get in, you use an admin container. Updates are image-based: the new OS image is written to a second partition and the node reboots into it, so a node is either on the old image or on the new one and never in between.

<DeckFig name="p4-bottlerocket-anatomy" />

For GPU nodes in particular, the nice part is that the EKS-optimised `aws-k8s-nvidia` variant ships the whole NVIDIA stack inside the image: the [driver](https://docs.nvidia.com/datacenter/tesla/index.html), the [container toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/index.html), the Kubernetes [device plugin](https://github.com/NVIDIA/k8s-device-plugin), the [MIG manager](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-operator-mig.html) and the [fabric manager](https://docs.nvidia.com/datacenter/tesla/fabric-manager-user-guide/index.html). In order, they let the operating system use the GPU, let a container see it, tell the [kubelet](https://kubernetes.io/docs/reference/command-line-tools-reference/kubelet/) how many GPUs the node has so that a pod can ask for `nvidia.com/gpu: 1`, split a GPU into slices, and run the NVLink and NVSwitch fabric of multi-GPU HGX systems, which is not a concern on a g7e. There's nothing to install on the node and nothing to keep in step with the kernel. If you use the NVIDIA [GPU operator](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/index.html) on top, the AWS documentation says to disable the operator's installation of the driver, the toolkit and the device plugin, because they're already there.

The trade-off is the same property seen from the other side. The driver version is whatever the AMI carries, so changing it means changing the AMI, which means drift and node replacement, and you can't SSH in to poke at a misbehaving node. For a fleet of identical, replaceable inference nodes, that's the right trade: the nodes are cattle and the interesting state is in the pod. For a pet node you like to tinker with, it would be the wrong one.

Two smaller notes on the GPU plumbing. AWS now recommends the [NVIDIA DRA driver](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu) for new deployments on Kubernetes 1.34 and later, but dynamic [DRA](https://kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/) provisioning in Karpenter v1.15 is alpha and off by default, so we use the device plugin that already ships in the AMI, and our pod asks for `nvidia.com/gpu: 1`. And [MIG](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/index.html), which splits one GPU into isolated slices, exists on g7e but with fewer slices than the seven of an H100, so on a 96 GB card the biggest practical split is four 24 GB slices. A 27B model doesn't fit in one, which is why we don't use it.

That's the node layer. Karpenter turns a pending pod into a Ready GPU node on its own, and Bottlerocket makes sure the node arrives with the driver and the device plugin already in place. The next thing the pod needs is its weights.

## 3. The model server: vLLM and the Run:ai Model Streamer

We have a GPU node, so now we need the pod that runs on it: a vLLM server with the right flags, loading its weights from S3. First we go through the `vllm serve` command flag by flag, including the memory arithmetic that decides how many requests one pod holds. Then we put the command in a Deployment and turn that into a template. Finally we create the bucket, the identity that reads it, and the [Run:ai Model Streamer](https://docs.vllm.ai/en/latest/models/extensions/runai_model_streamer/) that loads the weights.

Part 3 introduced vLLM and its [PagedAttention](https://arxiv.org/abs/2309.06180), and told you to treat it as the default engine. Everything it does is driven by flags. Most defaults suit somebody else's workload, and a handful decide whether your pod starts, how many requests it holds, and what the metrics are called.

First the checkpoint. NVIDIA publishes an official NVFP4 build, [`nvidia/Qwen3.8-27B-NVFP4`](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4). It isn't pure FP4: the MLP layers and the output head are NVFP4, while the attention and linear-attention projections stay in FP8, the usual recipe for keeping accuracy. It weighs about 20.4 GiB. Part 2 made the point that a quantization format is only useful if a kernel speaks it, and the RTX PRO 6000 in a g7e is a Blackwell part with native FP4, so here the format is a speed-up and not just a memory saving. vLLM detects the quantization from the checkpoint's own config, so there's no `--quantization` flag below.

```bash
vllm serve s3://example-models-bucket/models/nvidia/Qwen3.8-27B-NVFP4/ \
  --served-model-name qwen38-27b-nvfp4 --host 0.0.0.0 --port 8000 \
  --load-format runai_streamer --model-loader-extra-config '{"concurrency":16}' \
  --tensor-parallel-size 1 --max-model-len 262144 --kv-cache-dtype fp8 --gpu-memory-utilization 0.90 \
  --max-num-seqs 64 --max-num-batched-tokens 8192 \
  --enable-prefix-caching --enable-chunked-prefill --async-scheduling \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}' \
  --reasoning-parser qwen3 --tool-call-parser qwen3_coder --enable-auto-tool-choice \
  --disable-access-log-for-endpoints /health,/metrics,/v1/models
```

Several of these flags are redundant at this version, and we keep them anyway: an explicit flag documents intent, and an explicit `--async-scheduling` turns a silent fallback into a startup error. We'll point out the redundant ones as we go.

### The served model name

The first argument is the model, and here it's an S3 prefix with a trailing slash instead of a [Hugging Face](https://huggingface.co/docs/hub/index) name. `--served-model-name` is the one flag in this block we never leave out. It sets the `model` field in every response, it's the name clients must send, and it becomes the `model_name` label on every vLLM metric. Without it the name defaults to the S3 URL, and your dashboards fill with bucket paths. Our name, `qwen38-27b-nvfp4`, is also what the gateway matches on in section 4.

### Weights: load format and the streamer

`--load-format runai_streamer` hands weight loading to the Run:ai Model Streamer, which we come back to at the end of this section. For an `s3://` path vLLM v0.32.0 switches to it by itself, so the flag is redundant here. The `--model-loader-extra-config` JSON accepts exactly three keys, `distributed`, `concurrency` and `memory_limit`, and rejects anything else. `concurrency` is the number of S3 clients, and 16 is the value from the vLLM documentation's own example.

### Memory: context, KV dtype and the utilization fraction

`--max-model-len 262144` is the model's native context, so it's also the default. Changing it doesn't change the size of the KV pool, only how vLLM does its worst-case accounting, and startup fails if one request of that length can't fit. `--kv-cache-dtype fp8` stores keys and values in 8 bits instead of 16, which halves the bytes per token. `--gpu-memory-utilization 0.90` is the fraction of the card vLLM may use. The default is 0.92, and we leave a little more outside the budget for the driver and for fragmentation. Raising it by 0.01 buys about a gigabyte.

Let's do the arithmetic behind these three once, because it's where Qwen3.8 differs from the dense models in parts 1 and 2. The numbers below come from the startup log of a running pod serving this model on a g7e.2xlarge with the same memory flags. That pod runs vLLM v0.28.0 and a different quantised build of the model, with 22.13 GiB of weights once loaded. The pool on your pod will differ a little, but the structure is the same.

<DeckFig name="p4-memory-budget" />

**Step 1: the budget.** The card shows 94.97 GiB to PyTorch. At 0.90, vLLM may use 85.47 GiB of it. The weights take 22.13 GiB, another 1.14 GiB sits outside PyTorch's allocator (the CUDA context and libraries), and a profiling run with a worst-case batch finds a peak of 2.94 GiB of activations. What's left is the KV cache pool: 59.26 GiB, which the log prints as `Available KV cache memory`. The [CUDA graphs](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/) are captured after that and take another 0.89 GiB that this version doesn't take out of the pool, so total use ends up about a gigabyte above the 85.47 GiB you asked for. That's what the 10 percent outside the budget is for.

**Step 2: two kinds of memory per request.** A dense model needs one kind: a key and a value for every token in every layer, which grows with the request. Qwen3.8-27B is a hybrid and needs two.

- **Attention memory grows with the request.** Only 16 of its 64 layers are full attention. Each stores 2 KiB per token at fp8 (a key and a value, 4 heads of 256 dimensions, one byte each), so the 16 layers cost 32 KiB per token, the figure part 2 computed. The multi-token prediction ([MTP](https://docs.vllm.ai/en/latest/features/speculative_decoding/mtp/)) head we enable below is a 17th attention layer, which makes it 34 KiB per token.
- **State memory is fixed per request.** The other 48 layers are [linear attention](https://arxiv.org/abs/2412.06464), which keeps no entry per token. Each layer keeps one fixed-size summary of everything it has read so far, called a recurrent state, and all 48 together are about 150 MiB whether the request is 100 or 100,000 tokens long.

vLLM keeps both kinds in one pool of equal-sized blocks, so one block size has to suit both. A state is far bigger than an ordinary 16-token attention block, so vLLM stretches the attention block until it's at least as big as a state. That's what the startup line `Setting attention block size to 1600 tokens to ensure that attention page size is >= mamba page size` says. One block is then 1,600 tokens times 34 KiB, which is 53.125 MiB. In the attention group a block holds 1,600 tokens of keys and values. In a state group it holds one copy of the state, and the 48 linear layers fall into three such groups, so one full copy of the state is three blocks. With [prefix caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/) and three speculative tokens, vLLM reserves five copies per request (two, plus one per speculative token), which is 3 times 5 = 15 state blocks, about 797 MiB.

<DeckFig name="p4-kv-block" />

**Step 3: what fits.** A request needs one attention block per 1,600 tokens, rounded up, plus the 15 state blocks. An 8,192-token request is 6 + 15 = 21 blocks, about 1.1 GiB. The pool holds 59.26 GiB divided by 53.125 MiB, which is 1,142 blocks, so it holds 54 such requests. The same arithmetic for other lengths:

| Request length | Attention blocks | State blocks | Blocks in total | Requests the pool holds |
|---|---|---|---|---|
| 2,048 tokens | 2 | 15 | 17 | 67 (`--max-num-seqs` caps it at 64) |
| 8,192 tokens | 6 | 15 | 21 | 54 |
| 65,536 tokens | 41 | 15 | 56 | 20 |
| 262,144 tokens | 164 | 15 | 179 | 6.38 |

The last row is the one the log confirms: `Maximum concurrency for 262,144 tokens per request: 6.38x` is exactly 1,142 divided by 179. The line before it, `GPU KV cache size: 1,672,449 tokens`, isn't a capacity. It's that 6.38 multiplied by 262,144, so don't read it as the number of tokens that fit.

Two things follow that you can feel in production. A short request is mostly state: at 2,048 tokens, 15 of its 17 blocks are state, so memory doesn't limit short requests and `--max-num-seqs` does. And prefix caching works on whole blocks, so a prefix hit always lands on a multiple of 1,600 tokens.

<DeckFig name="p4-prefix-grid" />

A shared system prompt of 1,000 tokens never hits at all, and one of 1,700 hits for the first 1,600. Keep that in mind when the routing and metrics sections talk about prefix reuse.

To read the same numbers on your own pod, three startup lines carry them: `Available KV cache memory` for step 1, `Setting attention block size to N tokens` for step 2, and `GPU KV cache size` with `Maximum concurrency` for step 3. The checkpoint in this post has different weights from the one in that pod, so expect a different pool size. The block size doesn't depend on the weights, so it should read 1,600 with these flags, and if it doesn't, trust the log.

### Scheduler: batch size, chunked prefill, async scheduling

`--max-num-seqs 64` caps the decode batch. The server default on a card this size is 1,024, which sizes runner buffers for a concurrency the KV pool above could never serve, so a lower cap is cheaper and matches what the pool can hold. Above about 4,000 tokens of context the cap isn't what limits you, the KV pool is, which is why the autoscaling section uses KV usage and queue depth and not batch size. `--max-num-batched-tokens 8192` is the per-step token budget and equals the default for a GPU of this class. It's the size of one prefill chunk and the room for decode and draft tokens. Larger makes long prefills faster and raises the activation peak, which comes out of your KV pool.

`--enable-prefix-caching` and `--enable-chunked-prefill` are both on by default for this model, so they're redundant. We write them out because the routing section depends on them. [Chunked prefill](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill) splits a long prompt into pieces of at most 8,192 tokens that interleave with decode, so one 100,000-token prompt doesn't freeze everyone else's output. Without it, the batch budget would have to be at least the context length. `--async-scheduling` overlaps CPU scheduling with GPU execution so the GPU isn't idle between steps.

### Speculative decoding with the model's own MTP head

`--speculative-config '{"method":"mtp","num_speculative_tokens":3}'` turns on [speculative decoding](https://docs.vllm.ai/en/latest/features/speculative_decoding/) in its multi-token prediction form. Qwen3.8 ships a small extra head in the same checkpoint that proposes the next few tokens. The main model verifies all of them in one forward pass, and every accepted token is a decode step you didn't pay for. Part 2 explained why decode is memory-bound: each step streams the whole model for one token, so getting several tokens per step is the most direct lever on decode speed. No separate draft model is needed. One thing to remember: `num_speculative_tokens` is mandatory for this checkpoint, because the layer count vLLM looks for is under `text_config`, where the automatic lookup doesn't find it, and omitting it fails at startup.

It isn't free, and the costs belong on the budget sheet. The head adds 0.79 GiB of weights and one more attention layer to the KV group, and each request holds three more state blocks. At 16,384 tokens of context that cuts the pool's concurrency by about 40 percent, from about 74 to about 44 requests, in exchange for faster decode. We haven't measured the acceptance rate. vLLM publishes `vllm:spec_decode_num_accepted_tokens` and `vllm:spec_decode_num_draft_tokens`, and the ratio of the two is the number to watch.

### Reasoning, tool calls and logging

`--reasoning-parser qwen3` splits the model's `<think>` block out of the answer. The chat template opens every assistant turn with `<think>`, as part 2 showed, so without the parser the reasoning lands in `message.content` and your clients get a wall of thinking. `--tool-call-parser qwen3_coder` and `--enable-auto-tool-choice` do the same for tool calls: the template renders them in the XML-ish Qwen3-Coder format, and the parser turns them back into the structured `tool_calls` that agent frameworks expect. The auto flag without a parser is refused at startup. Last, `--disable-access-log-for-endpoints` keeps the health probe and the metrics scrape out of the access log, because on a pod that is probed every few seconds and scraped continuously, that's most of the log.

We left a few flags out on purpose. `--trust-remote-code` isn't needed, because the architecture is natively supported, and it executes Python files from the bucket. `--shutdown-timeout` defaults to zero, which aborts in-flight requests when the pod is told to stop, so set it, together with `terminationGracePeriodSeconds`, if a rolling update must drain. `--generation-config` defaults to `auto`, so the sampling defaults come from `generation_config.json` in the bucket: clients that send no temperature get the model author's.

A Deployment keeps our vLLM pod running and replaces it when it dies. Here's the raw manifest, with the command from above inside the container spec:

The startup probe allows 120 tries at 10 seconds each, a 20 minute budget for streaming the weights, compiling and capturing the CUDA graphs. A vLLM pod doesn't answer `/health` until all of that is done, and going by the source, the probe gets connection refused until then. Twenty minutes is a budget, not a measurement: measure your own startup and set the number from that.

### Streaming weights from S3

The Run:ai Model Streamer is the reason the model argument can be an S3 prefix. Its job is to get tensors from object storage into GPU memory without a full copy to local disk in between. It reads [safetensors](https://huggingface.co/docs/safetensors/index) files with many threads, each tensor is read into a buffer in host memory, and the copy to the GPU for one tensor overlaps with the reads of the others. For S3 the transport is a native client, `concurrency` sets how many clients run, and the chunk size defaults to 8 MiB. Distributed streaming, where each rank reads a slice and broadcasts it, exists for tensor parallelism and is irrelevant to a one-GPU pod.

<DeckFig name="p4-streamer-pipeline" />

Here's how it compares with the alternatives. The default loader pulls from the Hugging Face Hub every time a pod starts, which puts egress, rate limits and a token in your startup path. The other common pattern is an [init container](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/) that copies the whole checkpoint to local disk before vLLM loads the directory. It's the simplest to reason about and works with any version, but the phases are strictly sequential and you pay for the disk. The streamer overlaps the two and needs no disk for weights, at the price of IAM plumbing and an `s3://` path. Streaming makes sense when scale-out latency matters and the node has RAM to spare. The init container is the boring path, and a sound default on an older vLLM.

### The bucket and the upload

Terraform creates the bucket that holds the weights. A bucket lives in one region, so it's one of the three things from section 1 that you redo when you change region.

```hcl
# terraform/s3.tf
# The weights bucket: versioned, encrypted, public access blocked.
# The vLLM pods read it through the Pod Identity role in pod_identity.tf.

resource "aws_s3_bucket" "models" {
  bucket = var.model_bucket_name
}
```

Terraform stops at the bucket. Getting the weights in is a separate step, run once per model, and it isn't Terraform. First the layout, which matters more than anything else here. The model argument is the prefix, and the safetensors files must sit directly under it, because the streamer doesn't recurse for weights. vLLM also downloads every non-weight file under the prefix to a local directory before the weights stream: `config.json`, `generation_config.json`, the tokenizer files and the chat template. If tokenizer files are missing, v0.32.0 doesn't fail early. The server dies after it has loaded the weights and captured the graphs, the most expensive possible moment to find out.

### The identity that reads the bucket

Credentials need no Kubernetes secret. The native client falls back to the standard AWS credential provider chain, which includes the web-identity token that IRSA injects and the container credentials that EKS Pod Identity provides. Both work. Terraform sets up Pod Identity, and IRSA is the alternative. Either way the role needs `s3:GetObject` on the objects and `s3:ListBucket` on the bucket, and nothing else.

### Host memory and MTP from S3

Now host memory, the number that's easiest to miss. With the default `memory_limit` of 40 GB, the streamer can hold the whole checkpoint in RAM while it loads, 20.4 GiB here, on top of per-tensor copies and the vLLM process itself, which in steady state is around 10 GiB. That's why the pod asks for 40 GiB and may use 48. A `g7e.2xlarge` with 64 GiB of RAM has room, but this is the number that makes a bigger checkpoint a different instance. You can trade speed for memory by setting `memory_limit`, and we haven't measured what that does to load time.

One piece of history will save you a detour. Speculative decoding with the MTP head used to fail when the weights came from S3. vLLM built the draft model's config from the local config-only directory instead of from the S3 URL, and the draft loader then found no safetensors there ([issue 42060](https://github.com/vllm-project/vllm/issues/42060)). The workaround was an init container that copies the weights to local disk. The fix landed in v0.29.0 and is in the release pinned here, but we have only looked at it at the config layer and haven't run MTP from S3 end to end on a GPU, and one open pull request argues it's incomplete in some cases. A residual cost remains in v0.32.0: the draft loader streams every safetensors file under the prefix again, so expect roughly twice the S3 reads while it loads. Test it once on a real GPU before you delete your init container.

That's the third gate. The node exists and has its driver, and the pod now has to pull about 20 GiB through one role, into a buffer, onto a GPU, and then compile. Everything between a Ready node and a Ready pod happens in this section, so it's where most of the measuring belongs.

## 4. Routing: the endpoint picker and Envoy AI Gateway

Our pods can serve the model, but nothing yet decides which pod gets which request. First we look at why that's hard for an LLM and how the endpoint picker solves it, then at the gateway that calls the picker, and finally we create the resources, raw YAML first and templates after.

Part 1 ended on the sentence that the unit of work is a token and not a request, and the consequence shows up the moment you have more than one replica. One request is a 200-token question and another is a 100,000-token agent transcript. One lands on a pod whose KV cache is nearly full and another on a pod that already holds its system prompt. A load balancer that treats them as interchangeable sends them wherever the wheel points next.

<DeckFig name="p4-round-robin-vs-epp" />

### The problem with a normal load balancer

Round robin and least-connections were designed for requests that cost roughly the same and carry no memory. LLM requests break both assumptions:

- They differ in cost by orders of magnitude, so equal request counts mean unequal load.
- A pod's waiting queue and its KV cache fill up independently of how many connections it has.
- The pod that served a prompt a moment ago is still holding that prompt's KV blocks, which is a reason to send the next request with the same prefix back to it.

Everything a good router needs to know lives inside the model servers, and it changes every few milliseconds. Think of a restaurant host: one who hands out tables in turn is round robin, and a good one knows which tables are full.

### The endpoint picker

The Kubernetes answer is the [Gateway API Inference Extension](https://gateway-api-inference-extension.sigs.k8s.io/). It adds one resource, the [`InferencePool`](https://gateway-api-inference-extension.sigs.k8s.io/api-types/inferencepool/), which names a set of model-server pods by label selector and points at an **endpoint picker**, usually shortened to EPP. The picker is the good host: it looks at every candidate pod and names the best one for each request. It's an [Envoy external-processing](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/ext_proc_filter) server. The gateway parks each request and sends its headers and body to the picker over [gRPC](https://grpc.io/), the picker answers with the address of one pod, and the gateway forwards the request to that pod directly. Pool membership comes from the Kubernetes API and not from the proxy: the picker watches the pool and its pods, and admits a pod only when its `Ready` condition is true. A pod that is still streaming its weights is simply not a candidate.

The production-grade picker lives in the [llm-d router](https://github.com/llm-d/llm-d-router) project, which is where the Gateway API Inference Extension project moved it in its v1.6.0 release. The extension itself now keeps the API and a minimal conformance picker. We use [llm-d](https://llm-d.ai/) router v1.0.0 and Inference Extension v1.6.2.

What a picker knows decides how good it is. A common summary says it scrapes metrics off every vLLM pod and sends the request to the pod with the best prefix-cache hit. The first half is true and the second half is not.

<DeckFig name="p4-three-signals" />

### The three signals

The picker learns about the pool through three paths, and only the first one touches the pods.

The first is a scrape. Every 50 milliseconds by default, the picker does an HTTP GET of `/metrics` on every pod in the pool, which in our simulation came to about 20 scrapes a second per pod. It keeps exactly five vLLM series from the response: `vllm:num_requests_waiting`, `vllm:num_requests_running`, `vllm:kv_cache_usage_perc`, `vllm:lora_requests_info` and `vllm:cache_config_info`. That's load, and only load. The picker does not read vLLM's prefix-cache hit counters.

The second is the picker's own bookkeeping, and it's where prefix awareness comes from by default. The picker turns each prompt into an estimate of its tokens and hashes it in chained blocks of 64. After every pick it records, in a per-pod in-memory LRU, which pod just received which block hashes. The next request with the same beginning is scored against that table, and the pods are never asked. To test this we pointed the real picker image at fake pods that expose no prefix metric at all. A repeated 600-token prompt still went to the same pod 20 times out of 20, while 20 unique prompts split 11 and 9.

The third is vLLM publishing its own cache events, so the picker knows exactly which blocks are resident. It's called precise prefix-cache routing, but it's opt-in, needs extra flags on vLLM, and isn't the default. We didn't run it.

### Scoring

The picker scores each candidate and picks the highest. Three scorers do the work: a queue scorer, a KV-cache scorer that returns one minus the pod's usage, and a prefix scorer that returns the fraction of the prompt's blocks the pod is recorded as holding. Each returns a number between 0 and 1, the final score is the weighted sum, and the built-in weights are queue 2, KV cache 2 and prefix 3. A hidden filter runs first. It removes pods whose waiting queue is above 5 or whose KV usage is above 0.8, unless that would remove all of them.

### Weights as an exchange rate

The weights are the part we don't leave to a default, because they're an exchange rate between three different currencies: waiting requests, KV cache and cache reuse. Take two pods, one warm for the prompt and one idle. With the stock weights the picker keeps sending everything to the warm pod until its KV usage reaches 0.79, and only the hidden filter stops it, at 0.85. A prefix weight of 3 is bigger than the whole range of the KV score, so memory pressure can never outvote a full prefix match. With weights of 2, 3 and 1 the choice flips between a warm-pod KV usage of 0.43 and 0.44, exactly where the arithmetic says it should: the idle pod's usage plus the ratio of the prefix weight to the KV weight.

<DeckFig name="p4-weights-exchange-rate" />

This happened to us in production. On an older router, with the prefix weight at 3, traffic stuck to a single pod until its KV cache was full, while the pool-averaged metrics we were autoscaling on stayed calm because the other pods were idle. The fix was to raise the KV weight from 2 to 3 and lower the prefix weight from 3 to 1. Keep that in mind for section 6: it's the best argument for scaling on the worst pod and not only on the average.

There's a second reason to keep the prefix weight low for this model. The picker's index works in 64-token blocks, and it has no idea that vLLM, for a hybrid model like Qwen3.8, only reuses cache in whole blocks of 1,600 tokens. A request that shares a 1,000-token prefix with a warm pod looks like a strong match to the picker and is a total miss to vLLM. That's an inference from two sources and not something we measured, but it points the same way as the production lesson.

### Envoy AI Gateway

The picker needs a gateway to call it, and the gateway has to understand that a request to `/v1/chat/completions` carries a model name in its body. That's the job of [Envoy AI Gateway](https://github.com/theagentrouter/agent-router). It builds on [Envoy Gateway](https://gateway.envoyproxy.io/), the controller that turns [Gateway API](https://gateway-api.sigs.k8s.io/) resources into [Envoy](https://www.envoyproxy.io/) proxy configuration, and adds a second controller on top, so we run two controllers. One naming note, because you'll see both names: from v1.2.0 the project is called Agent Router, but the API group, the charts and the images keep the old names, and so does this post.

<DeckFig name="p4-control-and-data-plane" />

The split between the planes is what matters. In the control plane, Envoy Gateway watches [`GatewayClass`](https://gateway-api.sigs.k8s.io/reference/api-types/gatewayclass/), `Gateway` and [`HTTPRoute`](https://gateway-api.sigs.k8s.io/reference/api-types/httproute/), and the AI Gateway controller watches its own resources and generates the HTTP routes and proxy extensions for them. In the data plane, the Envoy pod gains an extra container: an external-processing [sidecar](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/) called `ai-gateway-extproc` that reads the request body, finds the model name and writes it into a header. In our simulation the proxy pod showed 2 of 2 containers until the first route existed and 3 of 3 after it.

<DeckFig name="p4-request-path" />

Following one request through it:

1. The client sends an OpenAI-style call with a `model` in the body.
2. The sidecar reads that model and sets the header `x-ai-eg-model`, overwriting any value the client tried to send, so the model always comes from the body.
3. The route matches on that header.
4. The route's backend is the `InferencePool`, so the picker runs next and returns a pod address.
5. On the way back, the sidecar reads the token usage and records it.

Of the six custom resources in this release, we use one in the request path: [`AIGatewayRoute`](https://github.com/theagentrouter/agent-router/blob/v1.2.0/api/v1beta1/ai_gateway_route.go), plus the Gateway API ones around it. [`AIServiceBackend`](https://github.com/theagentrouter/agent-router/blob/v1.2.0/api/v1beta1/ai_service_backend.go) and [`BackendSecurityPolicy`](https://github.com/theagentrouter/agent-router/blob/v1.2.0/api/v1beta1/backendsecurity_policy.go) are for external providers and upstream credentials, `GatewayConfig` tunes the sidecar, and `MCPRoute` and `QuotaPolicy` are out of scope here.

### The controllers and their install order

The install order is where the documentation and reality part ways. Following the documented order, Envoy Gateway with the InferencePool add-on never becomes Ready, because the cluster role that lets it read `InferencePool` objects ships with the AI Gateway chart. The order that works is:

1. The InferencePool [CRDs](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/) (Inference Extension v1.6.2).
2. Gateway API v1.6.1 and the Envoy Gateway CRDs (v1.9.3).
3. The AI Gateway CRDs, then the AI Gateway controller (v1.2.0).
4. Envoy Gateway v1.9.3 last, with its own CRDs switched off (`crds.enabled=false`) and with the AI Gateway's `envoy-gateway-values.yaml` plus the InferencePool add-on values from `examples/inference-pool/` in the AI Gateway v1.2.0 repository.

Done by hand, this order came up cleanly in a minute and twenty seconds, with no restarts. Terraform owns the controllers, so here it is as code:

```hcl
# terraform/addons.tf (lines 1 to 78)
# The controller Helm releases, in the install order that leaves every
# component Ready: each controller needs the CRDs it reads to exist
# first, so the releases chain with depends_on. The GIE CRDs ship as a
# small local chart (charts/gie-crds/) because the release manifest is
# plain YAML, not a Helm chart.

resource "helm_release" "gie_crds" {
  name      = "gie-crds"
  chart     = "charts/gie-crds"
  version   = "1.6.2"
  namespace = "kube-system"

  depends_on = [module.eks]
}

# Gateway API and Envoy Gateway CRDs.
resource "helm_release" "gateway_crds" {
  name       = "eg-crds"
  repository = "oci://docker.io/envoyproxy"
  chart      = "gateway-crds-helm"
  version    = "v1.9.3"
  namespace  = "kube-system"

  values = [yamlencode({
    crds = {
      gatewayAPI   = { enabled = true }
      envoyGateway = { enabled = true }
    }
  })]

  depends_on = [helm_release.gie_crds]
}

# AI Gateway CRDs.
resource "helm_release" "ai_gateway_crds" {
  name             = "aieg-crd"
  repository       = "oci://docker.io/envoyproxy"
  chart            = "ai-gateway-crds-helm"
  version          = "v1.2.0"
  namespace        = "envoy-ai-gateway-system"
  create_namespace = true

  depends_on = [helm_release.gateway_crds]
}

# The AI Gateway controller. The ClusterRole it ships lets Envoy
# Gateway read InferencePool objects, which is why it is installed
# before the gateway below.
resource "helm_release" "ai_gateway" {
  name             = "aieg"
  repository       = "oci://docker.io/envoyproxy"
  chart            = "ai-gateway-helm"
  version          = "v1.2.0"
  namespace        = "envoy-ai-gateway-system"
  create_namespace = true

  depends_on = [helm_release.ai_gateway_crds]
}

# Envoy Gateway with the AI Gateway values files (vendored in values/,
# source and tag in each file's header). The CRDs are installed by the
# release above, so the chart's own copy is disabled.
resource "helm_release" "envoy_gateway" {
  name             = "eg"
  repository       = "oci://docker.io/envoyproxy"
  chart            = "gateway-helm"
  version          = "v1.9.3"
  namespace        = "envoy-gateway-system"
  create_namespace = true

  values = [
    file("${path.module}/values/envoy-gateway-values.yaml"),
    file("${path.module}/values/envoy-gateway-values-addon.yaml"),
    yamlencode({ crds = { enabled = false } }),
  ]

  depends_on = [helm_release.ai_gateway]
}
```

The `depends_on` lines are the order. They make Terraform finish each step before it starts the next, instead of installing everything at once, which is what breaks. By hand, step 1 is a `kubectl apply` of the release manifest and the rest are `helm upgrade -i` commands, in the same order.

### The router chart

The router itself ships as a Helm chart, `oci://ghcr.io/llm-d/charts/llm-d-router-gateway`, version v1.0.0. It creates the `InferencePool` and the picker with its Service, so there's nothing for us to template. We only write values:

```yaml
# k8s/epp-values.yaml
# Helm values for the llm-d router chart (oci://ghcr.io/llm-d/charts/llm-d-router-gateway, version v1.0.0).
# Install with the release name qwen38-27b-nvfp4 in the namespace llm: the chart then creates the InferencePool and the
# endpoint picker Service under that name, which is what the AIGatewayRoute refers to.
router:
  modelServers:
    matchLabels:
      app: qwen38-27b-nvfp4     # the label on the vLLM pods
    targetPorts:
      - number: 8000
  epp:
    pluginsConfigFile: "balanced-plugins.yaml"
    pluginsCustomConfig:
      balanced-plugins.yaml: |
        apiVersion: llm-d.ai/v1
        kind: EndpointPickerConfig
        plugins:
        - type: queue-scorer
        - type: kv-cache-utilization-scorer
        - type: approx-prefix-cache-producer
          parameters:
            autoTune: true            # take LRU capacity (num_gpu_blocks) from the scraped vllm:cache_config_info
            blockSizeTokens: 64       # used when auto-tune has no scrape yet; values below 64 are clamped up to 64
            lruCapacityPerServer: 31250
        - type: prefix-cache-scorer   # reads the match info the producer wrote; the weight below is its vote
        - type: max-score-picker
        schedulingProfiles:
        - name: default
          plugins:
          - pluginRef: queue-scorer
            weight: 2
          - pluginRef: kv-cache-utilization-scorer
            weight: 3
          - pluginRef: prefix-cache-scorer
            weight: 1
          - pluginRef: max-score-picker
  monitoring:
    prometheus:
      auth:
        enabled: true             # the default: /metrics needs a bearer token (see the metrics section)
```

Three parts matter:

- `matchLabels` and `targetPorts` are the pool's selector: the label on our vLLM pods and the port they serve on, 8000.
- `pluginsCustomConfig` holds the picker's own config file, and `pluginsConfigFile` says which one to use. The plugins are the scorers from above, and the scheduling profile gives the weights we settled on: queue 2, KV cache 3, prefix 1. `autoTune` takes the LRU capacity from the scraped `vllm:cache_config_info`, and `blockSizeTokens` is the block size used before the first scrape (values below 64 are clamped up to 64).
- `monitoring.prometheus.auth.enabled` keeps the picker's `/metrics` behind a bearer token, which is the default. We come back to that in the next section.

The config is read only at startup and parsed strictly, so a typo is a crash loop and not a silent default. That's what you want: you find out at once. The install is one command:

```bash
helm upgrade -i qwen38-27b-nvfp4 oci://ghcr.io/llm-d/charts/llm-d-router-gateway \
  --version v1.0.0 --namespace llm --create-namespace -f epp-values.yaml
```

The release name is the model name on purpose. The chart derives the `InferencePool` name from it, and our route refers to the pool by that name.

Two more things about running the picker. The first is the failure mode. The `InferencePool` has a `failureMode` field whose API default is `FailClose`, and the llm-d chart overrides it to `FailOpen`. In the simulation we stopped the picker and sent 20 requests each way. With fail-open, 20 of 20 succeeded, split 10 and 10 by the proxy's fallback round robin. With fail-closed, 20 of 20 returned HTTP 500 with an empty body. Fail-open means unoptimised and not down, and that's what we want from a router, because a router is an optimisation. The second is the cost: the chart's default request for the picker is 8 CPUs and 8 GiB, because scraping scales with the number of pods. Size it as part of the platform and not as an afterthought.

### The Gateway

The Gateway gives the model an address. Here's the raw YAML:

```yaml
# k8s/gateway.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: ai-gateway
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
---
apiVersion: v1
kind: Namespace
metadata:
  name: ai-gateway
---
# per-Gateway Envoy settings; on EKS the Service is a LoadBalancer (add your AWS Load Balancer Controller annotations)
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: llm-gateway-proxy
  namespace: ai-gateway
spec:
  provider:
    type: Kubernetes
    kubernetes:
      envoyService:
        type: LoadBalancer
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: llm-gateway
  namespace: ai-gateway
spec:
  gatewayClassName: ai-gateway
  infrastructure:
    parametersRef:
      group: gateway.envoyproxy.io
      kind: EnvoyProxy
      name: llm-gateway-proxy
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: All   # let AIGatewayRoutes in the model namespace (llm) attach
```

The fields that matter:

- The `GatewayClass` ties the name `ai-gateway` to Envoy Gateway's controller, which is how Envoy Gateway knows these gateways are its to manage.
- The [`EnvoyProxy`](https://gateway.envoyproxy.io/docs/tasks/operations/customize-envoyproxy/) holds per-Gateway proxy settings, reached through `infrastructure.parametersRef`. Ours makes the proxy's Service a `LoadBalancer`, which on EKS is how it gets an AWS load balancer, and it's where your AWS Load Balancer Controller annotations go.
- The listener is HTTP on port 80, and `allowedRoutes.namespaces.from: All` lets routes in other namespaces attach. We need that, because the Gateway lives in `ai-gateway` and our route lives next to the model, in `llm`.

### The route

The `AIGatewayRoute` ties a model name to the pool. Here's the raw YAML:

```yaml
# k8s/aigatewayroute.yaml
apiVersion: aigateway.envoyproxy.io/v1beta1
kind: AIGatewayRoute
metadata:
  name: qwen38-27b-nvfp4
  namespace: llm
spec:
  parentRefs:
    - group: gateway.networking.k8s.io
      kind: Gateway
      name: llm-gateway
      namespace: ai-gateway
  llmRequestCosts:           # also makes the gateway force stream_options.include_usage on streamed requests
    - metadataKey: llm_input_token
      type: InputToken
    - metadataKey: llm_output_token
      type: OutputToken
    - metadataKey: llm_total_token
      type: TotalToken
  rules:
    - name: qwen38-27b-nvfp4
      matches:
        - headers:
            - type: Exact
              name: x-ai-eg-model
              value: qwen38-27b-nvfp4   # must equal vLLM --served-model-name
      timeouts:
        request: 300s   # default is 60s; a long streamed answer needs more
      backendRefs:
        - group: inference.networking.k8s.io
          kind: InferencePool
          name: qwen38-27b-nvfp4
```

The fields that matter:

- `parentRefs` attaches the route to the Gateway above.
- `llmRequestCosts` records the input, output and total token counts of each request. It also makes the gateway force `stream_options.include_usage` on streamed requests, so streamed answers report their usage too.
- The match is the header `x-ai-eg-model`, and its value must equal the name vLLM serves. That's why section 3 insisted on `--served-model-name`: on the pool path the model name in the request body is passed to vLLM unchanged.
- `timeouts.request` is 300 seconds. The default is 60, which is shorter than a long thinking answer.
- `backendRefs` points at the `InferencePool` by name, the one the router chart created.

If the route lived in a different namespace from the pool, you'd also need a [`ReferenceGrant`](https://gateway-api.sigs.k8s.io/reference/api-types/referencegrant/), and in this release it needs two `from` entries, one for `AIGatewayRoute` and one for the `HTTPRoute` it generates. With only the first, requests get a 500. Ours share the `llm` namespace, so we don't need one.

### The simulation

Before a GPU is involved we want proof that the request path does what section 4 says, and that we can see it doing it. So we deployed the whole route on a local [kind](https://kind.sigs.k8s.io/) cluster. What we ran is a simulation: the real Envoy Gateway and AI Gateway, the real llm-d router v1.0.0 at its chart's default scheduling profile, three fake model servers, no GPU. Each fake is a small Python server that imitates vLLM's API, holds every request for a fake prefill and decode, and exposes metrics under vLLM's names. They take the place of the Deployment from section 3, with the same labels and port. From an empty kind cluster to a Programmed gateway and an Accepted route took about four minutes, with one retry and live image pulls.

Every result below comes from that simulation. It is evidence about the gateway and the picker, not about vLLM, a GPU or Qwen3.8, and the fake's own latencies and KV usage mean nothing.

The same request as above returned 200 with the model name, through a pod the picker chose. Our fake adds an `x-served-by` header saying which pod answered, which real vLLM doesn't. On a real cluster you read the pod from the picker's per-pod counters, used below.

The first picture is the picker's scoring arithmetic on toy numbers, not a measurement. It has three pods and eight requests, some sharing a long system prompt, and for each request the scores the picker would compute with its default weights, using section 4's formulas.

<DeckFig name="p4-run-simulation" />

It shows the shape you'd expect: the shared prompt pulls requests onto the pod that holds it, load pushes them off again, and when the warm pod's queue reaches 5 the filter removes it and the next request goes elsewhere. The queue, KV and cache numbers in the figure are toy values, as its caption says. The next table is real: we sent requests through the real gateway and picker to the three fake pods and counted where each one landed.

| What we sent | Requests | Pod A | Pod B | Pod C |
|---|---|---|---|---|
| The same long system prompt, one request at a time | 30 | 0 | 0 | 30 |
| A different prompt every time, one at a time | 30 | 11 | 11 | 8 |
| 20 different prompts released at the same instant (run 1) | 20 | 15 | 5 | 0 |
| The same burst again (run 2) | 20 | 0 | 13 | 7 |
| 12 senders on the shared prompt for 30 seconds | 737 | 245 | 238 | 254 |

The first row is the textbook case: with nothing else going on, a repeated prompt sticks to the pod that already has it, 30 out of 30. The last row is the correction. Under concurrent load it doesn't stay pinned. The first twelve requests all went to the warm pod, the following ones spilled to a cold pod that had the prefix cached within about a second, and by the fourth second the load was spread almost evenly. "A shared prefix concentrates traffic on one pod" is true for one request at a time and a poor description of a loaded system, where the prefix replicates and the pool balances.

The third and fourth rows are the unexpected part. Twenty requests released within a few milliseconds of each other don't balance: 15, 5 and 0 in one run, 0, 13 and 7 in the next, and 20, 0 and 0 in an earlier one. We haven't isolated the cause, so this is an inference. The picker scores each request from the load numbers it last scraped, every 50 milliseconds by default, so requests inside one scrape window see the same snapshot and make the same choice. The same twenty prompts sent 100 milliseconds apart spread 6, 4 and 10. The llm-d project's own recommended configuration adds in-flight accounting to the scoring and spread the identical burst 6, 7 and 7, though it differs from the default in more than that one plugin, and we ran it as an aside on the same pods. If you serve agents that fan out in parallel, a burst is your normal traffic, so test the default scheduling profile against one.

The bookkeeping adds up. Across the whole run, including a few scenarios the table leaves out, the client counted 878 requests, the fake pods counted 878, and the picker's `llm_d_epp_scheduler_attempts_total` counted 878, with the same split per pod. The picker's prediction of the prefix hit rate, 0.82, matched the fake pods' real rate, 0.82, though that's a weak test, because our fake cuts prompts into the same blocks the picker's estimator does.

### Where the numbers come from

Three places in this stack expose metrics, and they answer different questions.

<DeckFig name="p4-metric-birthplaces" />

The model servers expose vLLM's own metrics on their serving port, `/metrics` on 8000, describing what happens inside an engine: queues, the KV cache, token counts and latencies. The endpoint picker exposes its own on port 9090, describing what happens between the gateway and the pods: how many pods it sees, the average queue and KV usage across them, and how long it took to choose. The AI Gateway's sidecar exposes a third set on port 1064, named `aigw-admin`, with the OpenAI-style token and latency histograms the gateway sees. That port isn't in the pod's Prometheus annotations, which point only at Envoy, so it needs its own scrape job. In the simulation, pod service discovery found it because the sidecar's container port is named.

The picker's endpoint has one more catch: it's authenticated by default. Without a token it answers 401, with the default service account's token 403, and 200 only for a service account allowed `get` on the non-resource URL `/metrics`. The router chart doesn't create that permission for your scraper, so ours does. Here's the raw YAML: a namespace, a ServiceAccount, a ClusterRole, a binding and a token Secret.

```yaml
# k8s/epp-metrics-reader.yaml
# A ServiceAccount allowed to read the EPP /metrics endpoint. The EPP (llm-d Router v1.0.0, default
# --metrics-endpoint-auth=true) validates the bearer token with a TokenReview and then a SubjectAccessReview for
# "get" on the non-resource URL /metrics, so the ServiceAccount needs that one rule.
# The Secret below carries NO token in this file: Kubernetes fills the token in when it sees the annotation + type.
apiVersion: v1
kind: Namespace
metadata:
  name: monitoring
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: metrics-reader
  namespace: monitoring
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: metrics-reader
rules:
  - nonResourceURLs: ["/metrics"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: metrics-reader
subjects:
  - kind: ServiceAccount
    name: metrics-reader
    namespace: monitoring
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: metrics-reader
---
apiVersion: v1
kind: Secret
metadata:
  name: metrics-reader-token
  namespace: monitoring
  annotations:
    kubernetes.io/service-account.name: metrics-reader
type: kubernetes.io/service-account-token
```

The ClusterRole is the one rule that matters: `get` on `/metrics`, which is what the picker checks after it validates the caller's token. The binding gives it to the `metrics-reader` ServiceAccount. The Secret's type and its `kubernetes.io/service-account.name` annotation make Kubernetes fill in a token for that account, so the file carries no secret. Point your scraper at that token, or bind the role to the service account Prometheus already uses and give that account a token.

| Metric | What it tells you |
|---|---|
| `vllm:num_requests_waiting` | The queue. Zero when the engine keeps up, and the first thing to climb when it doesn't |
| `vllm:num_requests_running` | Requests in the current batch |
| `vllm:kv_cache_usage_perc` | KV cache usage as a fraction from 0 to 1, despite the name |
| `vllm:prefix_cache_hits_total` and `vllm:prefix_cache_queries_total` | Prefix cache hits and lookups, in tokens, not requests |
| `vllm:time_to_first_token_seconds` | Arrival to first token, so queue plus prefill |
| `vllm:inter_token_latency_seconds` | Time between streamed tokens |
| `vllm:e2e_request_latency_seconds` | Arrival to finish |
| `vllm:request_success_total{finished_reason}` | Finished requests, split into stop, length, abort and error |
| `vllm:num_preemptions_total` | Requests evicted from the batch and recomputed: KV pressure made visible |
| `vllm:prompt_tokens_total`, `vllm:generation_tokens_total` | Prefill and decode throughput. Prompt tokens include the cached ones |
| `vllm:spec_decode_num_accepted_tokens_total` over `vllm:spec_decode_num_draft_tokens_total` | MTP acceptance rate, present only when speculative decoding is on |
| `llm_d_epp_average_queue_size`, `llm_d_epp_average_kv_cache_utilization` | The picker's pool averages, per pod, published every 5 seconds |
| `llm_d_epp_ready_endpoints` | Pods the picker has fresh metrics for, which is not the same as Kubernetes Ready |
| `llm_d_epp_scheduler_e2e_duration_seconds` | How long the picker took to choose. In the simulation the p95 was 0.17 milliseconds |

A few of those need a warning. `llm_d_epp_ready_endpoints` counts pods whose metrics are fresh, and when it falls to zero the two average gauges don't drop: they freeze at their last value. A dashboard that only plots the averages looks calm while nothing is serving. The picker's time to first token is the whole response time unless the request was streamed.

The gateway's token histograms count only what the gateway itself saw, and a 503 that the picker generates when no pod is ready never reaches them. We scaled the pool to zero and the picker counted three errors while the gateway's error series stayed unchanged. So for the error rate at the edge, use `llm_d_epp_request_error_total` or Envoy's own response-class counters.

And a Prometheus that scrapes every ten seconds can't see a spike that lasts a second. Twelve simultaneous requests hit one four-slot pod, and the most Prometheus ever recorded waiting on any pod was two. The picker polls at 50 milliseconds. Your dashboard doesn't.

### Queries for a dashboard

Here are the queries to start with. They live in our Prometheus [recording rules](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/), so each expression can be pasted into a [Grafana](https://grafana.com/) panel or into a KEDA trigger, and swapping `[5m]` for `[$__rate_interval]` makes them follow the panel's zoom.

```promql
# prefix cache hit ratio: sum first, then divide (an average of per-pod ratios would be wrong)
sum by (model_name) (rate(vllm:prefix_cache_hits_total[5m]))
  / sum by (model_name) (rate(vllm:prefix_cache_queries_total[5m]))

# time to first token, p95 across all pods
histogram_quantile(0.95, sum by (le, model_name) (rate(vllm:time_to_first_token_seconds_bucket[5m])))

# queue: requests waiting, summed over pods
sum by (model_name) (vllm:num_requests_waiting)

# the hottest pod's KV cache usage, and the average for comparison
max by (model_name) (vllm:kv_cache_usage_perc)
avg by (model_name) (vllm:kv_cache_usage_perc)

# requests evicted from the batch per second
sum by (model_name) (rate(vllm:num_preemptions_total[5m]))

# generated tokens per second: the throughput that is actually yours
sum by (model_name) (rate(vllm:generation_tokens_total[5m]))

# share of finished requests that ended in an error
sum by (model_name) (rate(vllm:request_success_total{finished_reason="error"}[5m]))
  / sum by (model_name) (rate(vllm:request_success_total[5m]))

# the picker's view of the pool, one series: exactly what a KEDA trigger needs
max(llm_d_epp_average_queue_size{name="qwen38-27b-nvfp4"})
```

The hit ratio is the one people get wrong, so the arithmetic is in a figure. Take one pod with a 70 percent hit rate on 1,500 tokens and another with 50 percent on 3,000. The pool's ratio is 2,550 over 4,500, which is 56.7 percent, and the mean of the two ratios, 60 percent, is wrong because it ignores that one pod saw twice the traffic. Quantiles have a similar problem: `histogram_quantile` interpolates inside a bucket, so the answer is only as precise as the bucket edges, and vLLM's default request-phase buckets start at 0.3 seconds. A latency objective below 300 milliseconds needs custom buckets.

<DeckFig name="p4-hit-ratio" />

All thirty rules, with their unit tests, are in the examples (`queries.rules.yml` and `queries.test.yml`). The tests use synthetic series with the real metric names and labels, and each asserts an expected value, including the 56.7 percent. A first version of the rules file, run against the simulation's live data, returned data for 23 of its 29 rules. Four of the others were the autoscaling queries, which returned nothing because their selectors still held placeholder names. With the real names in place each returned exactly one series. The last two were the speculative-decoding rules, empty here because the fake server has no draft model. So when you point a dashboard at a new deployment, check that the selector matches a series: an empty panel and a healthy system look the same until you do.

## 6. Autoscaling with KEDA

Everything so far has been about getting one pod to serve well. Now the setup has to grow: when requests pile up, we need more pods, and the whole chain from section 1 to section 3 runs again for each new one. We'll pick the signals, see how KEDA sits on top of the [HPA](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/), then write the [ScaledObject](https://keda.sh/docs/latest/concepts/scaling-deployments/) and template it.

### Signals that mean something

Our two signals are the ones the previous section built queries for: how many requests are waiting, and how full the KV cache is. Queue depth is the cleanest overload signal there is. A healthy engine keeps it near zero, and it climbs exactly when demand exceeds capacity. KV utilization is the capacity signal: sustained values near 1 mean the engine is at its concurrency ceiling, and new requests queue or get preempted.

CPU and memory are poor signals. The vLLM process spends its life waiting on the GPU, so its CPU is flat at saturation, and a GPU that reads 100 percent busy doesn't say whether it's busy and healthy or busy and drowning. Time to first token is a useful lagging safety net: users feel it, but it moves after the queue does.

### KEDA and the HPA

The Horizontal Pod Autoscaler is the built-in controller that changes a Deployment's replica count from a metric. KEDA doesn't replace it, it drives one. It creates and manages an HPA for our Deployment, serves our Prometheus query to it as an external metric, and takes over the one step the HPA can't do: the move between zero and one replica. So there are two controllers and one ladder of replica counts, and each owns a rung.

<DeckFig name="p4-keda-ownership" />

KEDA owns 0 to 1, polling every 30 seconds (`pollingInterval`). The HPA owns 1 to N: it syncs every 15 seconds, takes the maximum of whatever its triggers ask for, and applies the `behavior` we configure.

### The ScaledObject

The ScaledObject is KEDA's own object. It names the Deployment to scale, the replica bounds and the triggers that decide the count. Here's the raw YAML, validated against the KEDA v2.21.0 schema:

```yaml
# k8s/scaledobject.yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: qwen38-27b-nvfp4
  namespace: llm
spec:
  scaleTargetRef:
    name: qwen38-27b-nvfp4          # the vLLM Deployment
  minReplicaCount: 1                # a floor: scale-out is slow (node, image, weights), so never start from zero
  maxReplicaCount: 8
  fallback:
    # if a Prometheus trigger fails 3 polls in a row, hold 2 replicas instead of trusting a broken metric
    failureThreshold: 3
    replicas: 2
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0
          policies:
            - type: Pods
              value: 2              # at most 2 new replicas a minute: each one is slow to become useful
              periodSeconds: 60
        scaleDown:
          stabilizationWindowSeconds: 300
          policies:
            - type: Percent
              value: 100
              periodSeconds: 15
  triggers:
    # mean queued requests per pod, as the endpoint picker sees it. A per-pod average is not additive,
    # so the metric type is Value: desired = ceil(current replicas x value / threshold)
    - type: prometheus
      name: queue
      metricType: Value
      metadata:
        serverAddress: http://kube-prometheus-stack-prometheus.monitoring.svc:9090
        query: max(llm_d_epp_average_queue_size{name="qwen38-27b-nvfp4"})
        threshold: "2"
    # the hottest pod's KV cache utilization (0 to 1); an average would hide one saturated pod
    - type: prometheus
      name: worst-pod-kv-cache
      metricType: Value
      metadata:
        serverAddress: http://kube-prometheus-stack-prometheus.monitoring.svc:9090
        query: max(vllm:kv_cache_usage_perc{model_name="qwen38-27b-nvfp4"})
        threshold: "0.7"
    # an on-hours floor: inside the window this acts as a dynamic minimum, and the triggers above can push higher
    - type: cron
      name: business-hours
      metadata:
        timezone: UTC
        start: 0 8 * * 1-5
        end: 0 18 * * 1-5
        desiredReplicas: "2"
```

Five fields carry the design.

**`minReplicaCount: 1`.** Scaling to zero is tempting for expensive GPUs, but a cold start is a pending pod, a new node from Karpenter, an image pull, twenty gigabytes of weights, a torch compile, a CUDA graph capture, and only then a [readiness probe](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/#define-readiness-probes). None of those hops is short. There's a deeper problem too: our signals are emitted by the pods themselves, so at zero replicas there's no series and the scaler reports zero. Scaling up from zero would need an external activation signal, such as a gateway-side queue. That's our inference from how KEDA treats empty results, not an upstream guarantee, but it's enough to keep a floor of one.

**The 15 and 30 seconds.** We don't set `pollingInterval`, so KEDA's 30 seconds applies, with one change in KEDA 2.21. When `minReplicaCount` is above zero and you aren't using `idleReplicaCount`, `useCachedMetrics` or `scalingModifiers`, KEDA stops polling on its own schedule and reuses the values from the HPA's queries. That's our case, so our metrics effectively refresh every 15 seconds, not 30. Before the HPA's first query, KEDA still queries the sources itself.

**The `cron` trigger.** During business hours it's a dynamic minimum. The HPA takes the maximum over all triggers, so the cron's 2 sits under the demand-driven triggers, which can still push above it.

**`fallback`.** If Prometheus becomes unreachable, a broken query would freeze the scaler at whatever it last computed. After three failed polls in a row, `fallback` holds two replicas instead, a known-safe count.

**`behavior`.** Scale-up is capped at two new replicas a minute, because each one is slow to become useful. Scale-down waits a 300-second window first.

### Value or AverageValue

The line in that YAML most examples get wrong is `metricType: Value`. KEDA's default is `AverageValue`, and the two do different arithmetic. With `AverageValue` the HPA computes the desired replicas as the metric divided by the threshold, ignoring how many replicas it has now. That's right for a total, like all waiting requests summed across pods. With `Value` it computes the current replicas times the metric over the threshold. That's right for a number that's already per pod, like an average queue length or a utilization.

<DeckFig name="p4-value-vs-averagevalue" />

Take four replicas whose average queue is 3, against a threshold of 2. Under `AverageValue` the answer is `ceil(3 / 2) = 2`, so the autoscaler scales down while every pod has a queue. Under `Value` it's `ceil(4 x 3 / 2) = 6`, which is what we want. A per-pod KV utilization under `AverageValue` is worse: it can never exceed 1, so with a threshold of 0.6 it can never ask for more than 2 replicas, whatever the load.

The second rule is that the query must return exactly one series. KEDA's Prometheus scaler fails with `returned multiple elements` the moment it gets two, and two are easy to get by accident: two Prometheus replicas, or a bare selector that matches every pod. The `max(...)` in both queries collapses the series to one. For the KV trigger it also means we scale on the hottest pod, because an average would hide one saturated pod.

## 7. Tiered KV caching

The last lever makes every request cheaper by making fewer of them start from scratch. Recall the KV cache from part 2: the keys and values of every token already processed, kept so the next token doesn't recompute them. Here the KV pool is about 59 GiB of GPU memory, as the pod's startup log reports. When it's full the engine evicts, and an evicted prefix that comes back must be prefilled again. A g7e node has two other places to keep it: 64 GiB of host RAM, and a 1.9 TB local NVMe drive that so far has only been formatted. Tiered caching lets vLLM spill KV blocks from the GPU to the CPU and from the CPU to that drive, and bring them back when a prefix returns.

### How the tiers work

The mental model most of us start with is that blocks move down a tier when the tier above is full, like a CPU cache. That's wrong for this feature. In vLLM v0.32.0 blocks are written through. As each chunk of a prompt finishes, it's copied from the GPU to the CPU tier and then cascaded to every secondary tier, immediately. Eviction afterwards only drops one copy: the GPU drops its block, the CPU tier drops its least recently used one, and the NVMe copy stays. When a later request has the same prefix, the lookup goes GPU first, then CPU, then disk. A hit is loaded back from the nearest tier that has it, and a disk hit is staged through CPU RAM, so it costs two hops.

<DeckFig name="p4-tier-ladder" />

Two things follow. The CPU tier is bounded and evicts. The NVMe tier isn't: it grows until something deletes files, and vLLM doesn't, so a disk you don't watch eventually fills. And a chunk is not a token. The unit is a whole attention block, which for this model is 1,600 tokens (section 3), so a prefix shorter than one chunk can never be served from an external tier.

<DeckFig name="p4-prefix-hit-tiers" />

### Sizing the tiers

Each token costs 32 KiB of attention KV at fp8, so a 16 GiB CPU tier holds about 524,000 tokens, and an 800 GiB budget on the NVMe holds about 26 million. That 32 KiB is a floor, so measure the real bytes per token on your own pods from the offload counters. Each cached prompt also stores a recurrent-state snapshot of roughly 147 MiB. That's small against a 64,000-token prompt and large against a short one, which is one more reason tiering pays for long shared prefixes and not for short ones.

Why 16 GiB and not more? The CPU tier lives in `/dev/shm`, which counts against the pod's memory limit. On a 64 GiB node the pod also needs the streamer's buffer, which can hold the whole 20 GiB checkpoint while it loads, and about 10 GiB for the vLLM process itself. A 24 GiB tier would put us at the edge of what the node can allocate. Check your node's allocatable memory before you choose.

### The node side

The node needs the one setting we made in section 2: `instanceStorePolicy: RAID0` on the `EC2NodeClass`. It formats the NVMe and makes it the node's ephemeral storage, so an `emptyDir` lands on it. Without it the `emptyDir` sits on the EBS volume and the exercise is pointless, so the pod fails closed: it requests ephemeral storage that only a node with instance store can offer, and stays Pending anywhere else.

- **A wrapper around the start command.** The container runs `rm -f /dev/shm/vllm_offload_*.mmap; exec vllm serve "$@"`. The tiering spec can leave its memory-mapped file behind after a hard crash (vllm#57303), and a container restart keeps a memory-backed `emptyDir`, so without the `rm` the next start would find it already full.
- **The connector argument.** The CPU tier alone is two flags, `--kv-offloading-size 16` and `--kv-offloading-backend native`, and they give you nothing else. The NVMe tier needs the full connector configuration, passed as one JSON argument, `--kv-transfer-config`. In it, `cpu_bytes_to_use` is the 16 GiB in bytes (17179869184), and `secondary_tiers` holds one `fs` tier at `/kv-nvme/kv-offload` with 16 read and 16 write threads.
- **Resources and volumes.** Memory is 52Gi for request and limit, up from 40Gi and 48Gi. The ephemeral-storage request of 1050Gi and limit of 1100Gi are what make the pod fail closed. The `/dev/shm` volume grows from 8Gi to 20Gi (the 16 GiB tier plus slack), and a new `emptyDir`, `kv-nvme`, is mounted at `/kv-nvme` for the disk tier.
- **A sidecar, `kv-guard`.** It does the thing vLLM won't: it deletes the oldest block files once the NVMe directory passes a byte budget, here 800 GiB.

### The guard sidecar

The sidecar's script lives in a ConfigMap:

```yaml
# k8s/kv-guard-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: kv-guard
  namespace: llm
data:
  guard.sh: |
    #!/bin/sh
    # Keep $ROOT under $BUDGET_GIB GiB by deleting the oldest block files (FIFO by mtime).
    # FIFO, not LRU (relatime makes atime unreliable); a hot but old prefix is rewritten on its next miss.
    # GUARD_ONCE=1 runs a single pass (used by the test).
    BUDGET_KIB=${BUDGET_KIB:-$((BUDGET_GIB * 1024 * 1024))}
    while :; do
      used=$(du -sk "$ROOT" 2>/dev/null | cut -f1)
      if [ "${used:-0}" -gt "$BUDGET_KIB" ]; then
        find "$ROOT" -type f -name '*.bin' -exec stat -c '%Y %n' {} + \
          | sort -n | head -n "${BATCH:-200}" | cut -d' ' -f2- | xargs -r rm -f
        sleep 1
        continue
      fi
      [ -n "$GUARD_ONCE" ] && exit 0
      sleep "${INTERVAL:-30}"
    done
```

It's a loop that measures the directory and, while it's over budget, deletes the oldest files by modification time. That's first in first out, not least recently used, because access time on an NVMe filesystem isn't reliable, and a hot prefix that gets deleted is simply written again on its next miss. In a container test with ten one-megabyte files and a budget of about five megabytes, it removed the six oldest and left the newest four. The budget is 800 GiB on a drive that shows about 1.9 TB because the node's images and logs share it, and the kubelet starts evicting before the disk is full.

### Watching the tiers

A tier you can't see is a tier you can't trust, and vLLM v0.32.0 exposes what you need:

- `vllm:prompt_tokens_cached_by_source_total` splits the cached tokens into device, host and disk. It exists only from v0.32.0.
- `vllm:external_prefix_cache_hits_total` over `vllm:external_prefix_cache_queries_total` is the hit ratio of the CPU and disk tiers together.
- The `vllm:kv_offload_tiering_*` series break it down per tier, labelled `0:primary` for the CPU and `1:fs` for the disk.

Run it as a canary before you trust it. If the external hit counter never rises, either your prefixes are shorter than a chunk, or you're on a version where hybrid models with speculative decoding store blocks and never serve them. That bug existed in v0.28.0 and was fixed in v0.30.0.

### Limits and unknowns

We did not run this on a GPU, so there's no speed-up figure here, and you should be suspicious of any you see without a method. The sources we can point to say the tier helps when prompts share long prefixes that the GPU pool can't keep, such as agent loops and large system prompts, and doesn't when prefixes are short or unique.

The unknown that matters is the drive. AWS publishes only 4 KiB IOPS for the g7e local NVMe, 275,000 reads and 137,500 writes a second on the 2xlarge, and no throughput in megabytes per second. Run [`fio`](https://fio.readthedocs.io/en/latest/) on a node with large sequential reads and writes before you decide what the NVMe tier is worth, and compare the result with how fast the GPU recomputes the same prefix.

Two more limits to plan around. The tier is local to the pod: it's gone when the node is replaced, and it isn't shared between replicas. And the endpoint picker doesn't know it exists. It has no producer for local disk, and its index is sized from the GPU's block count, so routing doesn't change for a prefix that lives on the disk.

The tiers decide how much of a returning request can be skipped, and they're the reason the local drive from section 1 earns its place on the bill of materials.

## Putting it together

That's the whole stack, so let's step back and look at what we built. One `terraform apply` creates everything that lives in AWS: the network, the EKS cluster, the AWS side of Karpenter, the bucket for the weights, the permissions that let a pod read it, and the controllers we need (Karpenter, the gateway, KEDA and Prometheus). Two Helm commands then deploy the model: the llm-d router release, and our `llm-serving` chart with the GPU nodes, vLLM, the route, the autoscaler and the rules.

Along the way we followed the three steps from the start. We provisioned the infrastructure: a region and a machine that exist, Karpenter and Bottlerocket to turn a pending pod into a ready GPU node, and vLLM streaming 20 GiB of weights straight from S3. We set up the routing: a gateway that reads the model name from the request body, and an endpoint picker that sends each request to the best pod based on its queue, its KV cache and the prefixes it remembers sending. And we made the whole thing observable and autoscalable: metrics from vLLM and the picker, [PromQL](https://prometheus.io/docs/prometheus/latest/querying/basics/) queries on top of them, KEDA scaling on the queue and on the worst pod's KV cache, and a CPU and NVMe tier to keep more prefixes around.

If you take three habits from this part, make them these:

- Write the name the model is served under in one place and let everything else derive from it. The route, the metrics label and the probe all depend on it.
- Scale on the worst pod and on the queue, never on an average or on a utilization number that can't tell busy from drowning.
- Read the numbers that depend on your hardware off your own logs. The pool size, the block size and the startup time are all printed when the pod starts.
