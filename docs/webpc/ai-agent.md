# AI Agent

`/pc/apps/ai-agent/` embeds a local agent in the WebPC desktop, with image input on the Qwen models (LFM3 is text-only). The publishable authored source is `src/apps/ai-agent/`; the Astro route supplies its local asset base. `scripts/pc/prepare-ai-agent.mjs` rebuilds `public/pc/vendor/ai-agent/` from an explicit source allowlist and SHA-256-verified dependencies. No home-directory path is needed by a clean build. There is no server inference, account, Backyard SDK, speech permission, wake word, TTS, ASR or avatar.

## Runtime and data

Load model is explicit. Before that action, no model worker, WASM runtime or model weights are fetched. The app checks for WebGPU and shader-f16 support before loading. All three retained choices use immutable Hugging Face revisions in `models.js`:

| Model | Approximate first model download | Revision | License |
| --- | --- | --- | --- |
| [Qwen3.5 0.8B ONNX OPT](https://huggingface.co/onnx-community/Qwen3.5-0.8B-ONNX-OPT) | 600 MB | `9a4c21d8f724176b0a7edaaed36303044451886e` | Apache-2.0 |
| [Qwen3.5 2B ONNX OPT](https://huggingface.co/onnx-community/Qwen3.5-2B-ONNX-OPT) | 1.4 GB | `ed446636739bf426e73c5a00714fd8e010d36c21` | Base model Apache-2.0; conversion repository has no separate license metadata |
| [LFM3 1.7B ONNX](https://huggingface.co/LiquidAI/LFM3-1.7B-ONNX) | 1.4 GB | `57c125dfa29f2d39157e280b1d1f7480b8736d8d` | [LFM Open License v1.0](https://huggingface.co/LiquidAI/LFM3-1.7B-ONNX/blob/57c125dfa29f2d39157e280b1d1f7480b8736d8d/LICENSE) |

The model weights are not shipped with the website. The first load fetches from Hugging Face and its delivery hosts; completed downloads may remain in the browser cache. GPU memory needs exceed file size. Browser/device support varies; no CPU fallback or universal mobile support is claimed. These small models can answer incorrectly or miss tool calls. The LFM model has separate commercial-use conditions; consult its actual license.

The Qwen models also ship an optional vision encoder submodel that is **not** fetched on the text-only load: about 62 MB for the 0.8B model and about 197 MB for the 2B model. It downloads only when Image input is enabled on a loaded model or when the first image is sent. LFM3 has no image input.

The app keeps streaming, model-prefix cache reuse, timestamped user prompts, tool-call parsing, repeated-call/turn budgets and context compaction. Compaction summarizes older turns only after a nonempty summary completes, retaining recent paired tool calls/results. It does not silently drop history when summarization fails. Replies render as literal text, including Markdown/code syntax, never executable HTML. Thinking/tool markup is withheld.

Image input (Qwen models only) accepts PNG, JPEG and WebP up to 10 MB. The browser decodes and downscales the image (longest side 768 px) before it reaches the model worker, and the UI states that the extra vision encoder is about 62 MB (0.8B) or about 197 MB (2B). Image turns prefill without text-prefix cache reuse, but Stop still interrupts mid-prefill and mid-decode. Image pixels are **never stored**: the saved and exported conversation keeps only a text marker such as `[image: chart.png, 768×512]` in the user message, and after a reload the marker renders without the image. The settings dialog states this.

Cloud model (optional, opt-in per session): the two local options can be replaced, per session, by a user-keyed cloud model — (A) Claude via the bundled Anthropic SDK (`vendor/anthropic-sdk.mjs`, esbuild bundle of `@anthropic-ai/sdk@1.11.0`) and (B) any OpenAI-compatible Chat Completions endpoint (base URL + model + key, via `fetch`). Local models remain the default. The API key lives **only in memory**: it is never written to localStorage, IndexedDB, exports or logs, and the key plus the opt-in are cleared on reload, on New chat, and when the user switches back to a local model (or between cloud providers). Before the first cloud request, the settings dialog shows the opt-in — "your prompts, tool results and any attached image are sent to `api.anthropic.com` / the host in your base URL" — and the user confirms it with a key entry and an explicit "I understand" button. Base URLs must be https (enforced in code; the page has no CSP `connect-src` restriction because GitHub Pages cannot set response headers). The existing tools, their budgets, allow-lists and untrusted-data treatment apply unchanged: the same tool table is mapped to native Anthropic tool definitions (`strict`, `additionalProperties: false`, `eager_input_streaming`) and to OpenAI function schemas; every parsed tool input is validated against its schema before running, invalid inputs become error tool_results, and all tool results for a turn go back in one user message. Opus 5.5 request rules are honored: no `thinking`, no `temperature`/`top_p`/`top_k`, no assistant prefill, `tool_choice: {type:"auto"}`, `output_config.effort` (low/medium/high, default medium), `max_tokens` 64000, and server-side fallbacks on (`betas: ["server-side-fallback-2026-07-01"]`, `fallbacks: "default"`). A final `stop_reason: "refusal"` renders `stop_details.category` and explanation as a visible chat notice. Cloud turns use the same Stop/New chat/model-change termination (an abort signal, not a worker); the key and opt-in survive a Stop but not a New chat.

Stop, changing models, New chat and cached desktop close terminate the worker, including model download, prefill and decoding. Loading again reuses completed browser cache entries. Turn identities and abort signals prevent old tool results, summaries or replies from entering a new chat. The desktop's `pcBeforeClose` hook stops inference and rejects close while a save is pending or an unexported write failed; Retry save or Export resolves that state. Page unload warns for unsaved work. Minimizing preserves the chat and allows the current request to finish.

Chrome built-in AI (optional, feature-detected, on-device): where the browser offers its built-in foundation model, the model select gains a per-session option "Chrome built-in · on-device" (`LanguageModel`, the Prompt API). It appears only when `LanguageModel.availability()` reports anything but `unavailable` (`downloadable` counts: the Load button then starts Chrome's own model download from a user gesture, with progress shown from the documented `monitor` downloadprogress events). The backend is streaming text chat with **no tool calls** — the Prompt API has no tool calling and the agent never emulates it — and honors the same Stop, New chat, model-change and close contracts as the other backends (Stop aborts the in-flight prompt signal). Each turn creates a fresh on-device session seeded with the full history via `initialPrompts`, so the agent's own compaction and stored chat stay the source of truth. Privacy: the model runs on the device; per Chrome's documentation the only network traffic is the initial model download, and "no data is sent to Google or any third party when using the model." Requirements (Chrome's docs): desktop Chrome (Windows 10/11, macOS 13+, Linux, or Chromebook Plus), at least 22 GB of free space on the profile volume, and a GPU with strictly more than 4 GB of VRAM or 16 GB of RAM with 4 cores. Settings lists the documented `availability()` state of the four built-in APIs used here (Prompt API, Translator, Summarizer, Language Detector — stable on the web from Chrome 148 / 138 / 138 / 138; Writer and Rewriter are developer-trial only and intentionally not used), so a user can see why something is missing. The on-device tools are offered only when their API reports `available` — a model-initiated `create()` has no user gesture, which Chrome may need to start the download — and for each API that reports `downloadable`, Settings offers a “Download \<API\> model” button; that click is the user gesture (it calls `create()` with the documented `monitor`, progress in the status line) and on success availability is re-checked so the tool appears. If a tool call still fails (for example a download race), its tool_result is a clear error that tells the model to suggest that Settings button.

Four tools remain, plus three file tools offered to every backend while at least one Files grant is active (below), plus `search_files` while a search index exists, plus `run_code` for the Linux guest (below), plus three on-device Chrome tools offered to every backend only when the matching built-in API reports `available` (a `downloadable` API first needs the user to press its Settings “Download … model” button; the tools run on the page, not in the model worker; the on-device chat backend itself gets none, as it cannot call tools):

- `calculate`: an arithmetic-only expression evaluator.
- `web_search`: keyless Wikipedia search; the query goes to Wikipedia.
- `http_get`: direct CORS fetch with omitted credentials, restricted to domains mentioned by the user or returned by search. Extracted text is bounded and treated as untrusted. Page nodes are never mounted in the live document. If direct reading fails, Jina Reader is **off by default**; enabling it explicitly sends requested URLs, including query strings, to that provider. The preference resets on page load and desktop close. There is no paywall bypass promise.
- `run_javascript`: a fresh opaque-origin `sandbox="allow-scripts"` iframe hosts a blob worker with a network-blocking CSP. Parent/worker messages are authenticated by their source window; execution has a five-second timeout and bounded output. Abort removes the iframe and its worker. No hard per-run memory ceiling is supplied.
- `run_code` (Linux guest): runs `code` (up to 10,000 characters) in the Linux Terminal app's Alpine guest over the same-origin `BroadcastChannel('webpc-terminal')` to its exec service. `lang` is `python`, `node` or `sh` (SQL via Python's `sqlite3`); optional `timeout_ms` (1–120000, default 30000) interrupts the run with Ctrl+C and returns the partial output. The terminal app shows its approval prompt and the user approves every run (Deny focused first); the reply is `{exitCode, output, truncated}` (output at most 64 KB, the tail). If the terminal app is not open, or the run/approval is still pending past the limit plus 60 s, a readable error is returned instead (`not-running`, `denied`, `busy`, `timeout`, `no-terminal`). Guest output is untrusted tool data like the others; with a cloud model it is sent to that provider like any other tool result.
- `translate` (Chrome Translator API): `text`, `target_language` and optional `source_language` (BCP 47 codes; source defaults to English — call `detect_language` first when unknown). Input bounded at 4,000 characters; the first call per language pair may trigger Chrome's own model download, announced in the status line.
- `summarize` (Chrome Summarizer API): `text` and optional `type` (`key-points` default, `tldr`, `teaser`, `headline`); 4,000-character bound.
- `detect_language` (Chrome Language Detector API): returns the detected BCP 47 code and confidence for text up to 4,000 characters.

All three on-device results are untrusted tool data like the others; the same budgets and allow-lists apply.

Your files (optional, per-session grants): the settings dialog offers “Give the agent access…”, which opens the shared Files picker (`picker.mjs`, extended with a `select: 'file' | 'folder' | 'any'` option that keeps its existing behavior for Craft and Media) in a mode that accepts folders and files. Each selection becomes a grant, listed with a Revoke button. Grants are per session: they live only in page memory, are cleared on reload, New chat and desktop close, and are never written to localStorage, IndexedDB or exports. While at least one grant is active, three tools are offered to every backend (local, cloud, Chrome), wired through the same registry with schemas, input validation and budgets as the others:

- `list_files`: the entries of a granted folder or a subfolder of it (500 entries max, with a truncation flag).
- `read_file`: text files only (txt, md, csv, json, html, xml, js, py and similar; UTF-8, at most 200 KB). Binary content, invalid UTF-8 and unsupported types produce a clear error; PDFs produce an error pointing to PDFCraft.
- `write_file`: creates or updates a file inside a granted **folder** (a file grant alone grants no writes; the parent folder must already exist; content at most 200,000 characters). Every write shows a confirmation dialog with the resolved path, size and first lines, and announces overwrites. After a write the app broadcasts `{type: 'changed'}` on `BroadcastChannel('webpc-files')`, so an open Files page refreshes.
- `search_files`: semantic search over the granted files, offered only while the in-memory index has chunks (below). `query` (200 characters) and optional `k` (integer 1–10, default 5). Returns top-k chunks as `{path, score}` (score 0–1, two decimals) plus a snippet of at most 400 characters. The query embedding and the ranking (brute-force cosine) run on this device.

Tool paths are relative to the grant root and resolved by a pure resolver (`file-tools.js`): `..` segments, absolute paths, backslashes, control characters and paths over 200 characters are rejected; `..data` and `...` are ordinary names; matching is case-sensitive; the first matching grant wins (with several overlapping folder grants, the order in the grant list decides). File contents in tool results are untrusted tool data like the others. Privacy: with a cloud model, file contents the agent reads are sent to that provider — the settings text says so, and the grant status repeats it when a cloud model is active.

Semantic search over granted files (optional, on demand): the grants panel offers “Build search index”. Only that click downloads the embedding model — **Xenova/all-MiniLM-L6-v2**, Apache-2.0, pinned to immutable Hugging Face revision `751bff37182d3f1213fa05d7196b954e230abad9`, `onnx/model_quantized.onnx` (q8, about 23 MB) — and indexes anything. The model runs in its own small worker (`embed-worker.js`, separate from the chat model worker) through the vendored Transformers.js `pipeline('feature-extraction', …)` with `pooling: 'mean'`, `normalize: true` on the WASM device, so no WebGPU is needed. Indexed files are the granted text files under the same text and size rules as `read_file` (UTF-8, at most 200 KB; binary/PDF/other types are skipped and counted). Each file is chunked into about 800 characters with about 100 of overlap, preferring paragraph then line boundaries. The index stores vectors (Float32Array) plus path, chunk text and offset, and is **memory only**: it is cleared on reload, New chat and close, and revoking a grant drops that grant's chunks (a `search_files` call after the index becomes empty returns a clear error; the tool is simply not offered). Total indexed text is capped at 5 MB, with a clear count beyond it. A `changed` message on `BroadcastChannel('webpc-files')` re-indexes only files whose size or mtime moved — unchanged files are skipped — and a Cancel button aborts the download or the indexing run. The index never leaves the device; with a cloud model, the query text and the returned snippets (untrusted tool data) are sent to that provider like any other tool result.

The network tools necessarily reveal their search terms or requested URLs to the destination; this is not an entirely offline assistant. Tool data is not trusted as instructions. Outside granted files, the app has no filesystem/other-app access.

## Save and recovery contract

The existing idb-keyval database is reused, with new keys `pc:ai-agent:conversation:v1` and `pc:ai-agent:previous:v1`. On the **same origin**, valid `voice-agent:conversation` data is copied to the new key if it is absent; the legacy record is never moved or deleted. `voice-agent:model` is read as a fallback; its key is kept. Different origins cannot read one another's local data: export JSON from the old origin and use Settings → Open backup in the new app.

Current record corruption, initial read errors and failed migration block automatic replacement. New chat/Open explicitly retain the old raw record in the previous slot and replace atomically; quota failure leaves the stored records unchanged. Writes are serialized snapshots, so a previous turn's save cannot overwrite a later New chat. The current in-memory chat remains exportable after write failure. Raw export includes current/previous/legacy records for recovery. Import validates structure and size before replacing the current conversation. There is one previous record, not a permanent version archive; export important work.

## Source migration and provenance

The original private source folder was fully inspected and backed up outside public output before editing. Its local database and configuration were preserved. Runtime modules were rewritten as a text application; obsolete avatar modules/tests and unused display fonts were removed. Private deployment instructions, `.claude` tooling, `.backyard-data`, service config, tests and the external backup are absent from generated public assets.

The original copies of Transformers.js **4.3.2** and ONNX Runtime Web **1.31.0-dev.20260914-8d85527a0** were verified byte-for-byte against their npm archives. The matching split WASM is reconstructed at byte 14,000,000. Readability **0.6.0** has a deterministic CommonJS-to-ESM footer adapter; idb-keyval **6.2.1** has an attribution comment only. No hand edits are made to minified libraries. Preparation verifies all source hashes, even on a cached build; dependency files are generated/ignored. The first clean preparation fetches roughly 28 MB. No new npm dependencies are required.

Notices, upstream declarations and license copies are in `public/third-party/ai-agent/`. The pinned ORT dev npm package has no license files and its commit URL was unavailable during verification; its standard MIT and broad third-party notices were obtained from the public v1.24.2 source tag. This is documented as a provenance limitation, not an exact inventory of that dev build's transitive native dependencies. Declared JS dependency notices are included; version labels are minimum declared ranges, not a reconstructed upstream build lockfile. Replacing ORT independently of Transformers is not recommended without rerunning real inference.

## Verification

`downloadable` and `unavailable` do not), the Settings `chromeDownload` user-gesture helper (documented `create()` options per API, monitor progress, re-check flow), the on-device tool schemas and input bounds, a failed tool call (e.g. a `NotAllowedError` race) returning a clear error that names the Settings download button, executor caching with download status lines, and the on-device chat client (streaming, history sent as `initialPrompts`, Stop abort, `QuotaExceededError` mapping, and no tool schemas sent to a backend without tool calling). `tests/pc-ai-agent-files.test.mjs` covers the grant path resolver (escape attempts, absolute paths, backslashes, control characters, case sensitivity, `..`-style names like `..data`, overlong input, file-vs-folder grants, write gating and the first-grant-wins rule), text/binary detection and the 200 KB read bound, the write preview (path, size, first lines, overwrite notice), the file tools' gating/schemas/input bounds, the grant-aware system prompt, and that a persisted conversation record never carries grants. `tests/pc-files-picker.test.mjs` covers the picker's accept filtering and the new `select` visibility filter (default file mode unchanged). A mocked-Claude headless browser check (`.lanes/scratch/ai/check-ai2.mjs`) exercised the grant flow through the picker, a `list_files` + `read_file` round-trip, `write_file` with its confirmation dialog and a BroadcastChannel refresh of an already-open Files page, a rejected `../` escape (no file created, no dialog), reload clearing the grants, the sentinel OPFS-root audit, and zero unexpected external requests. `tests/pc-ai-agent-search.test.mjs` covers the chunker (empty/tiny files, hard breaks with exact overlap, paragraph-then-line boundary preference), cosine top-k (ties keep the earlier index, k clamping), the skip-unchanged metadata logic, the 5 MB char budget, revoke dropping exactly one grant's chunks, result shaping (2-decimal score, 400-char snippet), the `search_files` tool gating/schema/k bounds, and that the pure index modules use no storage APIs. A mocked-Claude headless browser check (`.lanes/scratch/ai/check-ai3.mjs`) stubs the embedding worker with a deterministic fake embedding (hashed bag-of-words, 64 dimensions, through a worker-URL route), then verifies the build button (with the 23 MB note), the on-demand index build, a `search_files` turn ranking the right file first, a `changed` broadcast re-indexing only the edited file (unchanged files skipped), revoke dropping the tool, reload clearing the index, the sentinel OPFS-root audit and zero unexpected external requests (the stubbed worker fetches nothing, so zero huggingface.co). A separate real-model run (`.lanes/scratch/ai/check-ai3-real.mjs`) loaded the real `embed-worker.js` with the actual model — every model file fetched at the pinned revision, and the only external hosts huggingface.co and its `*.hf.co` CDNs (Transformers.js 4.3.2’s `pipeline()` progress pre-fetch additionally touches revision `main`, which resolves to the same commit and is a one-time browser-cached extra download) — and confirmed related sentences score higher than unrelated ones (cosine 0.90 vs −0.03); it reports the 22.6 MB model size and the embedding wall time (32-chunk batch: 0.5 s). `tests/browser/pc-ai-agent.spec.mjs` uses a deterministic **model worker only** to test real UI, IndexedDB, tools, sandbox, proxy behavior, cancellation, close guards and mobile sizing. It does not claim to test model quality.

An additional manual Chromium smoke on an AMD RDNA 3 WebGPU adapter loaded the actual pinned Qwen3.5 0.8B model, generated a reply, cancelled a long prompt, then reloaded the model and generated again. Normal unflagged headless Chromium had no adapter and showed the supported unavailable state. The tested launch used `--enable-unsafe-webgpu --enable-features=Vulkan --use-angle=vulkan`; these are local test flags, not a requirement automatically imposed on visitors. The two larger model choices were retained with pinned metadata but were not downloaded for this smoke. Full cross-browser/GPU validation and model-quality evaluation are not claimed.
